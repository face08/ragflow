# 03 分块与批次构建

本文档描述 GraphRAG 主流程的第一阶段：如何从文档库拉取已有 chunk，并按 token 数量组装成批次供 LLM 抽取。

## 1. 前置条件

GraphRAG 任务启动前，文档必须已完成普通解析任务，即：

1. 文档已被 Parser 切分成 chunk（通过 `PipelineTaskType.PARSER` 任务）
2. Chunk 已写入文档库（Elasticsearch / Infinity / OpenSearch），带向量
3. Chunk 带 `doc_id`、`kb_id`、`tenant_id` 等字段可检索

GraphRAG 是**后置任务**，不重复解析文件，只在现有 chunk 之上做 LLM 抽取。

## 5. 加载单文档 chunk 并组装批次

核心函数 `load_doc_chunks` [index.py:323-350](file:///d:/work/rag/ragflow/rag/graphrag/general/index.py#L323-L350)：

```python
def load_doc_chunks(doc_id: str) -> list[str]:
    from common.token_utils import num_tokens_from_string

    chunks = []
    current_chunk = ""

    # 1. 从文档库拉取 chunk（按位置排序，全量拉取）
    raw_chunks = list(
        settings.retriever.chunk_list(
            doc_id, 
            tenant_id, 
            [kb_id], 
            fields=fields_for_chunks,  # ["content_with_weight", "doc_id"]
            sort_by_position=True,     # 保证顺序
            retrieve_all=True          # 不分页
        )
    )

    callback(msg=f"[GraphRAG] chunk_list returned {len(raw_chunks)} raw chunks for doc:{doc_id}")

    # 2. 提取 content_with_weight 字段
    contents = [
        content 
        for chunk in raw_chunks 
        if (content := chunk.get("content_with_weight", ""))
    ]

    # 3. 特殊处理：NER 方法不需要批次拼接
    if _select_extractor_type(graphrag_config) == "ner":
        return contents

    # 4. 按 token 数拼接批次
    for content in contents:
        if num_tokens_from_string(current_chunk + content) < batch_chunk_token_size:
            # 未超限，拼接
            current_chunk += content
        else:
            # 超限，保存当前批次，开启新批次
            if current_chunk:
                chunks.append(current_chunk)
            current_chunk = content

    # 5. 保存最后一个批次
    if current_chunk:
        chunks.append(current_chunk)

    callback(msg=f"[GraphRAG] chunk_list combine {len(raw_chunks)} raw chunks to {len(chunks)} chunks for LLM extraction for doc:{doc_id}")
    return chunks
```

### 5.1 为什么要拼接批次？

原因：

1. **LLM 上下文利用**：单个 chunk 可能只有几百 token，单独调用 LLM 浪费上下文窗口
2. **API 开销**：减少 LLM 调用次数，降低延迟和成本
3. **实体连贯性**：相邻 chunk 可能描述同一实体的不同侧面，拼接后 LLM 能识别得更准

### 5.2 NER 方法为何不拼接？

[index.py:335-336](file:///d:/work/rag/ragflow/rag/graphrag/general/index.py#L335-L336)：

```python
if _select_extractor_type(graphrag_config) == "ner":
    return contents
```

原因：NER（命名实体识别）用 spaCy 模型，不走 LLM，逐 chunk 处理即可，无需批次优化。

## 6. 批次构建示例

假设文档被切成 10 个 chunk，每个 500 token，`batch_chunk_token_size=4096`：

```
原始 chunk:
  chunk1: 500 token
  chunk2: 500 token
  chunk3: 500 token
  chunk4: 500 token
  chunk5: 500 token
  chunk6: 500 token
  chunk7: 500 token
  chunk8: 500 token
  chunk9: 500 token
  chunk10: 500 token

拼接后批次（4096 token 上限，实际约 8 个 chunk = 4000 token）：
  batch1: chunk1 + chunk2 + ... + chunk8  (4000 token)
  batch2: chunk9 + chunk10                (1000 token)
```

最终传给 LLM 的是 2 个批次，而非 10 次调用。

## 7. 并发加载与信号量

[index.py:354-405](file:///d:/work/rag/ragflow/rag/graphrag/general/index.py#L354-L405)：

```python
semaphore = asyncio.Semaphore(max_parallel_docs)  # 默认 4

subgraphs: dict[str, object] = {}
failed_docs: list[tuple[str, str]] = []
total_chunks = 0

async def build_one(doc_id: str):
    nonlocal total_chunks

    async with semaphore:
        # 检查是否已有子图（检查点命中）
        existing_sg = await load_subgraph_from_store(tenant_id, kb_id, doc_id)
        if existing_sg:
            subgraphs[doc_id] = existing_sg
            callback(msg=f"[GraphRAG] doc:{doc_id} subgraph found in store, skipping LLM extraction.")
            return

        # 加载 chunk
        chunks = load_doc_chunks(doc_id)
        total_chunks += len(chunks)
        if not chunks:
            callback(msg=f"[GraphRAG] doc:{doc_id} has no available chunks, skip generation.")
            return

        # 后续：LLM 抽取（下一篇详述）
        # ...

# 启动并发任务
tasks = [build_one(doc_id) for doc_id in doc_ids]
results = await asyncio.gather(*tasks, return_exceptions=True)
```

设计要点：

1. **信号量限流**：同时只有 `max_parallel_docs`（默认 4）个文档在处理，防止过多并发导致内存/数据库压力
2. **检查点优化**：先查是否已有子图，命中则跳过 LLM 抽取（容错设计，见后续章节）
3. **异步并发**：`asyncio.gather` 让多个文档并行处理，提升吞吐

## 8. 字段说明：content_with_weight

```python
fields_for_chunks = ["content_with_weight", "doc_id"]
```

`content_with_weight` 是 chunk 的主内容字段，包含：
- 文本内容
- 可能带有位置/权重元数据（具体格式依 Parser 而定）

GraphRAG 只关心文本部分，元数据在抽取阶段不参与 LLM 输入。

## 9. 增量判定？

**当前实现无增量判定**。每次 GraphRAG 任务都会：

1. 拉取全部 chunk
2. 检查子图检查点
3. 如果检查点不存在，重新走 LLM 抽取

未来可能的优化方向：
- 记录上次处理的 chunk 列表
- 新增 chunk 时只抽取新 chunk，增量合并图谱

但这需要更复杂的变更追踪机制，当前版本采用「全量重建」策略。

## 10. 容错设计：检查点命中

[index.py:369-373](file:///d:/work/rag/ragflow/rag/graphrag/general/index.py#L369-L373)：

```python
existing_sg = await load_subgraph_from_store(tenant_id, kb_id, doc_id)
if existing_sg:
    subgraphs[doc_id] = existing_sg
    callback(msg=f"[GraphRAG] doc:{doc_id} subgraph found in store, skipping LLM extraction.")
    return
```

`load_subgraph_from_store` 查询文档库中 `knowledge_graph_kwd=subgraph` 且 `source_id=doc_id` 的记录。如果存在，直接加载 networkx 图，跳过 LLM 调用。

这是**断点续传**机制的核心：
- 如果上次任务部分完成（某些文档已生成子图），重启任务时这些文档无需重跑
- 只有未完成的文档才会走 LLM 抽取

详见 [09-容错与性能设计.md](./09-容错与性能设计.md)。

## 11. 小结

分块与批次构建阶段的关键设计：

1. **前置依赖**：GraphRAG 依赖普通解析任务先完成分块
2. **批次拼接**：按 token 数（默认 4096）拼接相邻 chunk，减少 LLM 调用次数
3. **NER 特殊路径**：NER 方法不拼接，逐 chunk 处理
4. **并发控制**：信号量限制同时处理文档数，防止资源耗尽
5. **检查点优化**：已有子图的文档跳过 LLM 抽取，实现断点续传
6. **全量重建**：当前无增量判定，每次任务处理所有 chunk

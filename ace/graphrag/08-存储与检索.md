# GraphRAG 存储与检索

本文档详细说明 RAGFlow GraphRAG 模块中知识图谱的持久化策略、chunk 字段设计、检索流程与排序算法。

---

## 1. 问题陈述

GraphRAG 流程的最后两步是：

1. **存储**：将 NetworkX 图对象序列化为可检索的 chunk 结构，写入 Elasticsearch/Infinity；
2. **检索**：根据用户查询，从图数据中召回相关的实体、关系和社区报告，组装成 LLM 可用的上下文。

RAGFlow 的设计原则是：

- **图是一等公民**：完整的 NetworkX 图以 JSON 序列化形式存为一条 chunk（`knowledge_graph_kwd: "graph"`），支持快速重建；
- **节点和边也是独立 chunk**：每个实体、每条关系都有自己的嵌入向量和检索字段，支持向量相似度、PageRank、类型过滤等多维度检索；
- **子图快照**：每个文档生成一份子图副本（`knowledge_graph_kwd: "subgraph"`），用于增量更新和回滚；
- **Insert-then-prune**：新旧数据原子替换，崩溃时保留上一轮的完整状态。

## 2. 图的序列化与反序列化

### 2.1 get_graph - 从存储加载图

入口函数在 `utils.py:530-547`：

```python
async def get_graph(tenant_id, kb_id, exclude_rebuild=None):
    """Load the knowledge-graph for *kb_id* from the document store, rebuilding if marked removed."""
    conds = {
        "fields": ["content_with_weight", "removed_kwd", "source_id"],
        "size": 1,
        "knowledge_graph_kwd": ["graph"]
    }
    res = await settings.retriever.search(conds, search.index_name(tenant_id), [kb_id])
    if not res.total == 0:
        for id in res.ids:
            try:
                if res.field[id]["removed_kwd"] == "N":
                    g = json_graph.node_link_graph(
                        json.loads(res.field[id]["content_with_weight"]),
                        edges="edges"
                    )
                    if "source_id" not in g.graph:
                        g.graph["source_id"] = res.field[id]["source_id"]
                else:
                    g = await rebuild_graph(tenant_id, kb_id, exclude_rebuild)
                return g
            except Exception:
                continue
    result = None
    return result
```

核心逻辑：

1. 查询 `knowledge_graph_kwd: "graph"` 的唯一 chunk（size=1）；
2. 检查 `removed_kwd` 字段：
   - `"N"` → 图有效，用 `json_graph.node_link_graph` 反序列化；
   - `"Y"` → 图已被标记删除，调用 `rebuild_graph` 从子图 chunks 重建。
3. `removed_kwd` 是一个**软删除标记**。当知识库被删除或图被标记为陈旧时，不直接删除 graph chunk，而是把 `removed_kwd` 改为 `"Y"`，触发重建流程。

为什么要重建而不直接删？因为删除操作可能失败或不完整，保留 graph chunk 作为最后的回退选项。

---

### 2.2 NetworkX node-link format

RAGFlow 使用 NetworkX 的 `node_link_data` / `node_link_graph` 进行图的序列化和反序列化：

```python
# 序列化
json_graph.node_link_data(graph, edges="edges")

# 反序列化
json_graph.node_link_graph(json.loads(data), edges="edges")
```

生成的 JSON 结构：

```json
{
  "directed": false,
  "multigraph": false,
  "graph": {
    "source_id": ["doc1", "doc2"]
  },
  "nodes": [
    {
      "id": "Entity A",
      "entity_type": "PERSON",
      "description": "...",
      "source_id": ["doc1"]
    }
  ],
  "edges": [
    {
      "source": "Entity A",
      "target": "Entity B",
      "description": "...",
      "weight": 5
    }
  ]
}
```

**关键点**：

1. **`edges="edges"` 参数**：NetworkX 3.x 默认将边列表的 key 命名为 `"links"`，RAGFlow 显式指定为 `"edges"` 以保持与 Go 侧图解析的一致性。序列化和反序列化时必须使用相同的参数，否则会丢失边数据。

2. **图元数据 vs 节点属性**：`graph.graph["source_id"]` 是图级别的元数据（记录该图来自哪些文档），不是节点属性。节点的 `source_id` 属性记录该节点出现在哪些文档中。

### 2.3 rebuild_graph - 从子图重建

`rebuild_graph` 从 Elasticsearch 中加载所有 subgraph chunks，逐个反序列化并合并成完整图。

**完整代码**（`utils.py:869-903`）：

```python
async def rebuild_graph(tenant_id, kb_id, exclude_rebuild=None):
    graph = nx.Graph()
    src_ids = []
    flds = ["content_with_weight", "source_id"]
    bs = 256
    for i in range(0, 39*bs, bs):
        es_res = await thread_pool_exec(
            settings.docStoreConn.search, flds, [],
            {"kb_id": kb_id, "knowledge_graph_kwd": ["subgraph"]},
            [], OrderByExpr(), i, bs,
            search.index_name(tenant_id), [kb_id]
        )
        tot = settings.docStoreConn.getTotal(es_res)
        es_res = settings.docStoreConn.getFields(es_res, flds)
        for id, d in es_res.items():
            if d["source_id"][0] == exclude_rebuild:
                continue
            g = json_graph.node_link_graph(json.loads(d["content_with_weight"]), edges="edges")
            graph = graph_merge(graph, g, d["source_id"][0])
            src_ids.extend(d["source_id"])
        if len(es_res.keys()) < bs:
            break
    graph.graph["source_id"] = sorted(set(src_ids))
    return graph
```

**关键点**：

1. **分页查询**：每批 256 个 subgraph chunks，最多 39 批（约 10,000 个文档）。超过此规模需要考虑其他索引策略。

2. **`exclude_rebuild` 参数**：删除文档时，需要排除该文档对应的子图。通过 `if d["source_id"][0] == exclude_rebuild: continue` 跳过。

3. **`graph_merge` 合并逻辑**：逐个合并子图，节点和边的 `description` 字段用 `<SEP>` 拼接，`source_id` 字段合并为列表。

4. **子图机制的代价**：为了支持快速删除和增量更新，RAGFlow 同时存储完整图（graph chunk）和每个文档的子图（subgraph chunk）。存储空间接近翻倍，换取操作便利性。

### 3.1 阶段一：构造 graph 和 subgraph chunk

```python
chunks = []

# 完整图 chunk
graph_chunk = {
    "id": deterministic_uuid(kb_id, "graph"),
    "content_with_weight": json.dumps(json_graph.node_link_data(graph, edges="edges")),
    "knowledge_graph_kwd": "graph",
    "kb_id": [kb_id],
}
chunks.append(graph_chunk)

# 文档子图 chunk（如果提供了 doc_id）
if doc_id:
    node_ids = [
        n for n in graph.nodes
        if doc_id in graph.nodes[n].get("source_id", [])
    ]
    subgraph = graph.subgraph(node_ids).copy()
    
    # 改写节点属性：source_id 只保留当前文档
    for n in subgraph.nodes:
        subgraph.nodes[n]["source_id"] = [doc_id]
    
    subgraph_chunk = {
        "id": deterministic_uuid(kb_id, doc_id),
        "content_with_weight": json.dumps(json_graph.node_link_data(subgraph, edges="edges")),
        "knowledge_graph_kwd": "subgraph",
        "source_id": [doc_id],
        "kb_id": [kb_id],
    }
    chunks.append(subgraph_chunk)
```

**关键点**：

1. **诱导子图 + `.copy()`**：`graph.subgraph(node_ids)` 返回的是视图（view），修改会影响原图。`.copy()` 创建独立副本。

2. **改写 source_id**：子图中的节点可能在多个文档中出现，但子图 chunk 只记录当前文档，因此需要改写 `source_id` 为单元素列表。

3. **确定性 UUID**：`deterministic_uuid(kb_id, key)` 保证相同 key 生成相同 ID，使得更新操作可以覆盖旧 chunk。

---

### 3.2 阶段二：批量预热嵌入缓存

在 `set_graph` 早期版本中，节点和边的嵌入生成是逐个进行的：

```python
# 旧实现（伪代码）
for node in nodes:
    embedding = await embd_mdl.encode(node_text)  # 17k+ 次 round-trip
```

对于 17,000+ 个节点，这意味着 17,000+ 次网络往返，耗时巨大。现在的实现改为批量预热缓存：

```python
# 新实现（utils.py:665-677）
await _batch_embed_cache_misses(embd_mdl, cache_keys, encode_texts, tenant_id, kb_id)
```

**三步流程**：

1. **收集缓存未命中项**：遍历所有节点和边，检查其嵌入是否已在 Redis 缓存中。未命中的项收集到 `cache_keys` 和 `encode_texts` 列表中。

2. **批量嵌入生成**：调用 `embd_mdl.encode(encode_texts)` 一次性生成所有缺失的嵌入（内部会分批，但对外是单次调用）。

3. **批量写回缓存**：调用 `_write_embed_cache_batch` 将嵌入写回 Redis，每批 64 个（`_INSERT_BULK_SIZE = 64`），将 N 次写入收敛为 `ceil(N/64)` 次。

**节点 vs 边的缓存策略差异**：

- **节点**：cache key 和编码文本都是 `node_name`（实体名称）。
- **边**：cache key 是 `A->B`（节点对），编码文本是 `A->B: <description>`（包含关系描述）。

这样设计的原因：边的语义不仅取决于两端节点，还取决于关系类型和描述，因此必须将描述编码进嵌入中。

---

### 3.3 阶段三：节点转 chunk

遍历 `change.added_updated_nodes`，为每个节点生成 entity chunk：

```python
for node in change.added_updated_nodes:
    nhop_neighbors = n_neighbor(graph, node)
    await graph_node_to_chunk(
        kb_id, embd_mdl, node, graph.nodes[node],
        chunks, nhop_neighbors
    )
```

**`n_neighbor` 返回结构**：

```python
[
    {
        "id": "Neighbor A",
        "path": ["Entity X", "Neighbor A"],
        "weights": [5]
    },
    {
        "id": "Neighbor B",
        "path": ["Entity X", "Intermediate", "Neighbor B"],
        "weights": [3, 8]
    }
]
```

每个邻居包含：
- `id`：邻居节点名称
- `path`：从当前节点到邻居的路径（节点序列）
- `weights`：路径上每条边的权重

这些信息被序列化到 entity chunk 的 `n_hop_with_weight` 字段中，供检索时路径扩展使用。

---

### 3.4 阶段四：边转 chunk

遍历 `change.added_updated_edges`，为每条边生成 relation chunk：

```python
for f, t, a in change.added_updated_edges:
    await graph_edge_to_chunk(kb_id, embd_mdl, f, t, a, chunks)
```

其中 `f` 是源节点、`t` 是目标节点、`a` 是边属性字典。边不需要计算 N 跳邻居，因为边本身就是一跳关系。

---

### 3.5 阶段五：原子删除和插入

```python
# 先删除旧的 graph 和 subgraph chunk
await thread_pool_exec(
    settings.docStoreConn.delete,
    {"knowledge_graph_kwd": ["graph", "subgraph"]},
    search.index_name(tenant_id), kb_id,
)

# 再批量插入所有新 chunk
await insert_chunks_bounded(chunks, tenant_id, kb_id)
```

**为什么先删后插？**

Graph chunk 和 subgraph chunk 必须保证唯一性——一个知识库只能有一个完整图，一个文档只能有一个子图。如果直接插入，旧的 chunk 会残留（虽然 ID 相同会覆盖，但如果文档被删除，其 subgraph chunk 需要被清理）。

**代价**：删除和插入之间存在时间窗口，此期间图检索会失败或返回不完整结果。RAGFlow 的选择是优先保证数据一致性，牺牲短暂的可用性。对于知识图谱这种批量构建、低频更新的场景，这个权衡是合理的。

**`insert_chunks_bounded`**：内部按 `_INSERT_BULK_SIZE = 64` 分批插入，避免单次请求过大导致 Elasticsearch 拒绝。

## 4. Entity chunk 字段结构

`graph_node_to_chunk` 负责将图中的节点转换为可检索的 chunk。

**完整代码**（`utils.py:621-674`）：

```python
async def graph_node_to_chunk(kb_id, embd_mdl, ent_name, meta, chunks, nhop_neighbors=None):
    description = meta["description"]
    d = {
        "id": get_uuid(),
        "kb_id": [kb_id],
        "docnm_kwd": ent_name,
        "source_id": meta["source_id"],
        "content_with_weight": json.dumps({"name": ent_name, **meta}, ensure_ascii=False),
        "content_ltks": rag_tokenizer.tokenize(description),
        "knowledge_graph_kwd": "entity",
        "entity_kwd": ent_name,
        "entity_type_kwd": meta["entity_type"],
        "rank_flt": meta["rank"],
        "available_int": 0,
    }
    if nhop_neighbors is not None:
        d["n_hop_with_weight"] = json.dumps(nhop_neighbors, ensure_ascii=False)
    d["content_sm_ltks"] = rag_tokenizer.fine_grained_tokenize(d["content_ltks"])
    ebd = await get_embed_cache(embd_mdl.llm_name, ent_name)
    if ebd is None:
        ebd, _ = await embd_mdl.encode([ent_name])
        ebd = ebd[0]
        await set_embed_cache(embd_mdl.llm_name, ent_name, ebd)
    assert ebd is not None
    d["q_%d_vec" % len(ebd)] = ebd
    chunks.append(d)
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `entity_kwd` | keyword | 实体名称，用于精确匹配和聚合 |
| `entity_type_kwd` | keyword | 实体类型（PERSON/ORGANIZATION/...），用于按类型过滤 |
| `rank_flt` | float | PageRank 分数，反映实体在图中的重要性 |
| `q_<dim>_vec` | dense_vector | 实体名称的嵌入向量，用于语义相似度检索 |
| `n_hop_with_weight` | text | N 跳邻居的 JSON 序列化，检索时用于路径扩展 |
| `content_with_weight` | text | 节点完整属性的 JSON，供 LLM 消费 |

## 5. Relation chunk 字段结构

`graph_edge_to_chunk` 负责将图中的边转换为可检索的 chunk。

**完整代码**（`utils.py:677-728`）：

```python
async def graph_edge_to_chunk(kb_id, embd_mdl, f, t, meta, chunks):
    rel_desc = meta["description"]
    d = {
        "id": get_uuid(),
        "kb_id": [kb_id],
        "docnm_kwd": f"{f}->{t}",
        "source_id": meta["source_id"],
        "content_with_weight": json.dumps(
            {"from": f, "to": t, **meta}, ensure_ascii=False
        ),
        "content_ltks": rag_tokenizer.tokenize(rel_desc),
        "knowledge_graph_kwd": "relation",
        "from_entity_kwd": f,
        "to_entity_kwd": t,
        "weight_int": meta["weight"],
        "available_int": 0,
    }
    d["content_sm_ltks"] = rag_tokenizer.fine_grained_tokenize(d["content_ltks"])
    cache_key = f"{f}->{t}"
    encode_text = f"{f}->{t}: {rel_desc}"
    ebd = await get_embed_cache(embd_mdl.llm_name, cache_key)
    if ebd is None:
        ebd, _ = await embd_mdl.encode([encode_text])
        ebd = ebd[0]
        await set_embed_cache(embd_mdl.llm_name, cache_key, ebd)
    assert ebd is not None
    d["q_%d_vec" % len(ebd)] = ebd
    chunks.append(d)
```

**字段说明**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `from_entity_kwd` | keyword | 关系起点实体名称 |
| `to_entity_kwd` | keyword | 关系终点实体名称 |
| `weight_int` | integer | 关系权重，反映关系强度或出现频次 |
| `q_<dim>_vec` | dense_vector | 关系描述的嵌入向量（编码文本为 "A->B: description"） |

**关键区别**：边的嵌入编码的是 `"A->B: <description>"`，而不是单纯的节点对。这样可以区分同一节点对之间的不同关系类型。

## 6. 检索流程总览

`KGSearch.retrieval` 是知识图谱检索的入口函数，负责将用户问题转换为相关实体和关系，并返回结构化数据供 LLM 使用。

**完整流程**（`search.py:139-295`）：

```python
async def retrieval(self, question, embd_mdl, chat_mdl, **kwargs):
    # 第一阶段：查询改写与实体提取
    entity_types, entities = await self.query_rewrite(question, chat_mdl)
    
    # 第二阶段：按关键词检索实体
    ents_by_kwd = await self._search_entities_by_keywords(entities, embd_mdl)
    
    # 第三阶段：按类型检索实体
    ents_by_type = await self._search_entities_by_types(entity_types, embd_mdl)
    
    # 第四阶段：按文本检索关系
    rels = await self._search_relations_by_text(question, embd_mdl)
    
    # 第五阶段：N 跳路径扩展与打分
    all_ents = self._expand_and_score_paths(ents_by_kwd, ents_by_type, rels)
    
    # 第六阶段：类型加权与最终排序
    final_ents = self._apply_type_weighting_and_sort(all_ents, entity_types)
    
    # 第七阶段：社区报告检索
    reports = await self._community_retrieval_(final_ents[:topk])
    
    return self._format_as_dataframe(final_ents, reports)
```

这个流程体现了多路召回 + 多因子融合的经典检索范式。

## 7. 查询改写与实体提取

`query_rewrite` 使用 LLM 从用户问题中提取实体类型和具体实体。

**Prompt 模板**（`search.py:188-238`）：

```
---Role---
You are a helpful assistant tasked with identifying both entity types and entities
from the user's query.

---Goal---
Given the query, identify:
1. entity_types: the categories of entities relevant to answering the query
2. entities: the specific named entities mentioned in the query

---Output Format---
{
  "entity_types": ["organization", "person"],
  "entities": ["Apple Inc.", "Tim Cook"]
}
```

**后处理**：

1. JSON 解析结果并做健壮性校验（可能返回非法 JSON，需 fallback）
2. `entity_types` 归一化为小写
3. `entities` 保留原始大小写（因为要用于关键词匹配）
4. 如果提取失败，回退为空列表，此时后续检索退化为纯向量检索

**为什么不直接拿 question 做向量检索？**

用户问题通常包含大量与实体无关的语境词（"请帮我分析一下…"、"…的情况怎么样"）。直接编码整个问题会让向量偏离实体本身的语义中心。通过 LLM 抽取出实体名称后，用实体名称做向量检索能够更精准地对齐 entity chunk 的 `q_vec`（该向量正是由实体名称编码而来）。

## 8. 多阶段检索与打分

### 8.1 按关键词检索实体

对每个提取出的实体名称，先做向量检索，再做精确匹配加权：

```python
for ent in entities:
    ent_vec = await embd_mdl.encode([ent])
    res = docStoreConn.search(
        vector_query={"q_vec": ent_vec, "topk": ent_topn},
        filters={"knowledge_graph_kwd": ["entity"], "kb_id": kb_ids},
    )
```

召回的实体带上相似度 `sim`，作为后续打分的基础分。

### 8.2 按类型检索实体

对每个 `entity_type`，做精确匹配（terms 查询）：

```python
res = docStoreConn.search(
    filters={
        "knowledge_graph_kwd": ["entity"],
        "entity_type_kwd": entity_types,
        "kb_id": kb_ids,
    },
    orderBy=OrderByExpr().desc("rank_flt"),
)
```

按 PageRank 降序取 top-N，保证召回的是该类型下最重要的实体。

### 8.3 按文本检索关系

用原始 question 的嵌入检索 relation chunk：

```python
q_vec = await embd_mdl.encode([question])
res = docStoreConn.search(
    vector_query={"q_vec": q_vec, "topk": rel_topn},
    filters={"knowledge_graph_kwd": ["relation"], "kb_id": kb_ids},
)
```

这里直接用 question 的嵌入而不是抽取的实体，因为关系描述本身就是自然语言句子，与问题的表达形式更接近。

---

### 8.4 N 跳路径扩展与打分

检索到的关系 (A, B) 可能与召回的实体 E 不是直接邻居，但可能存在路径 E → ... → A 或 E → ... → B。通过 entity chunk 的 `n_hop_with_weight` 字段，可以计算路径得分：

```python
def path_score(entity, target, n_hop_neighbors):
    score = 0
    for neighbor in n_hop_neighbors:
        if neighbor["id"] == target:
            hop_index = len(neighbor["path"]) - 1
            score += entity.sim / (2 + hop_index)
    return score
```

**打分公式**：

```
path_score(E, T) = Σ (entity_sim / (2 + hop_index))
```

**关键设计**：

1. **距离衰减**：1 跳邻居除以 3，2 跳除以 4，3 跳除以 5…… 距离越远，贡献越小。
2. **多路径累加**：如果存在多条路径从 E 到 T，每条路径都贡献一次得分，反映"多重证据"的置信度提升。
3. **基于初始相似度**：entity_sim 来自第 8.1 阶段的向量检索，反映该实体本身与查询的相关性。

**为什么是 (2 + hop_index) 而不是 (1 + hop_index)？**

避免 0 跳（自环）时除以 1 导致得分过高。实际上 n_hop_neighbors 不包含自身，最小是 1 跳，分母从 3 开始。

---

### 8.5 类型加权

如果一个实体同时在"按关键词召回"和"按类型召回"中出现，说明它既与查询相关，又是查询关注的实体类型，置信度更高：

```python
for ent in entities:
    if ent in ents_by_kwd and ent in ents_by_type:
        ent.sim *= 2
```

这是一种简单的多路命中加权策略，类似于搜索引擎中的"标题匹配 + 正文匹配"双重加权。

---

### 8.6 最终排序

```python
final_score = entity.sim * entity.pagerank
entities.sort(key=lambda e: e.final_score, descending=True)
```

**贝叶斯视角**：

这个公式类似于贝叶斯后验：

```
P(entity | query) ∝ P(query | entity) × P(entity)
```

- `entity.sim`（向量相似度）类比 `P(query | entity)`：给定实体，它与查询的相关性
- `entity.pagerank` 类比 `P(entity)`：实体的先验重要性

两者相乘得到后验得分，同时考虑相关性和重要性。

**为什么不是 sim + pagerank？**

加法隐含线性独立假设，而实际上"不重要的实体即使相关也不应高排"、"重要的实体如果不相关也不应高排"。乘法更符合"两者皆备"的筛选逻辑。

## 9. 社区报告检索

社区报告是对一组紧密相关实体的高层总结，通过 `entities_kwd` 数组字段存储该社区包含的所有实体。

**完整代码**（`search.py:295-378`）：

```python
async def _community_retrieval_(self, top_entities, topk=5):
    entity_names = [e["entity_kwd"] for e in top_entities]
    
    # Terms 查询：entities_kwd 字段匹配任意 top entity
    res = await docStoreConn.search(
        filters={
            "knowledge_graph_kwd": ["community"],
            "entities_kwd": entity_names,
            "kb_id": self.kb_ids,
        },
        orderBy=OrderByExpr().desc("rank_flt"),
        limit=topk,
    )
    
    reports = []
    for doc in res:
        reports.append({
            "title": doc["title"],
            "content": doc["content_with_weight"],
            "rank": doc["rank_flt"],
        })
    return reports
```

**关键点**：

1. **`entities_kwd` 数组字段**：社区报告 chunk 的 `entities_kwd` 存储该社区的所有实体名称（数组）。Elasticsearch 的 terms 查询会匹配数组中包含任意指定实体的文档。

2. **按 PageRank 排序**：社区报告的 `rank_flt` 字段存储该社区的重要性分数（通常是社区内节点的平均或最大 PageRank）。返回最重要的社区报告。

3. **覆盖多个社区**：一个查询可能涉及多个社区（例如"Apple 和 Microsoft 的竞争关系"），通过 topk=5 返回多个相关社区的报告。

**报告 JSON 格式示例**：

```json
{
  "title": "科技公司生态系统",
  "content": "本社区包含 Apple、Microsoft、Google 等科技巨头，以及它们的产品、服务和竞争关系...",
  "rank": 0.87,
  "entities_kwd": ["Apple Inc.", "Microsoft", "Google", "iPhone", "Azure"]
}
```

## 10. 总结

RAGFlow 的 GraphRAG 存储与检索设计体现了以下核心思想：

1. **图是一等公民**：完整图作为独立 chunk 存储，删除时不需要逐个查询节点和边，一次删除即可清空。

2. **子图机制**：每个文档的子图单独存储，支持快速增量更新和删除，代价是存储空间接近翻倍。

3. **节点和边的可检索性**：节点和边不仅是图结构的组成部分，更是可独立检索的 chunk，带有向量、关键词、类型等多维索引。

4. **批量优化**：嵌入生成和缓存写入都采用批量策略，将 N 次 round-trip 收敛为 O(N/64)，显著降低网络开销。

5. **多路召回 + 多因子融合**：关键词、类型、向量、路径、PageRank 等多个维度协同工作，形成鲁棒的检索管道。

6. **一致性优先**：先删后插策略牺牲短暂可用性，保证 graph chunk 的唯一性和数据一致性。

7. **贝叶斯排序**：`sim × pagerank` 的打分公式同时考虑相关性和重要性，避免"高相关但不重要"或"高重要但不相关"的实体排在前面。

通过这些设计，RAGFlow 在保持图结构完整性的同时，提供了高效的向量检索和结构化查询能力，适配 LLM 驱动的问答场景。

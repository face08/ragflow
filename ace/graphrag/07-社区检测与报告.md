## 一、这个阶段解决什么问题

实体消解完成后，图谱里是"细粒度"的知识：一个个实体节点、一条条关系边。
但用户提问往往是**宏观**的："这份文档整体讲了什么？"、"X 团队和 Y 项目之间的整体关系是怎样的？"

单条实体描述无法回答这类问题。GraphRAG 的答案是：

1. 用图聚类算法（Leiden）把图切成若干**社区**（community）——社区内节点连接紧密，社区间连接稀疏；
2. 对每个社区调用 LLM 生成一份**结构化报告**（标题 / 摘要 / 影响评级 / 详细发现）；
3. 把报告作为独立 chunk 写入 Document Store，检索时可召回。

这样就在原子级知识之上叠了一层"摘要级知识"，形成 GraphRAG 论文里的 Global Search 能力基础。

## 三、Leiden 层次聚类

### 3.1 为什么是 Leiden

Leiden 是 Louvain 算法的改进版，解决了 Louvain 可能产出**内部不连通社区**的缺陷。RAGFlow 直接复用 `graspologic` 的 `hierarchical_leiden`，得到的是**层次化**结果：level 0 是最粗的划分，level 越大社区越细。

### 3.2 run() 的完整流程

```python
def run(graph: nx.Graph, args: dict[str, Any]) -> dict[int, dict[str, dict]]:
    max_cluster_size = args.get("max_cluster_size", 12)
    use_lcc = args.get("use_lcc", True)
    nodes = set(graph.nodes())
    if not nodes:
        return {}

    node_id_to_community_map = _compute_leiden_communities(
        graph=graph,
        max_cluster_size=max_cluster_size,
        use_lcc=use_lcc,
        seed=args.get("seed", 0xDEADBEEF),
    )
    levels = args.get("levels") or sorted(node_id_to_community_map.keys())
    ...
```

调用处是 `leiden.run(graph, {})`——**传空 dict**，所以全部走默认值：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `max_cluster_size` | 12 | 社区节点数上限，超过则继续递归细分 |
| `use_lcc` | True | 只对最大连通分量聚类 |
| `seed` | `0xDEADBEEF` | 固定随机种子，保证可复现 |
| `levels` | None → 全部层级 | 所有层级的社区都会生成报告 |

`use_lcc=True` 是个值得注意的取舍：孤立的小连通分量（比如某个只在一个 chunk 里出现、和主体知识无关的实体簇）会被直接排除在社区之外，不会生成报告。这减少了噪声报告，代价是这些边缘实体只能通过 entity/relation 级检索命中。

### 3.3 图稳定化：为什么要排序

```python
def _stabilize_graph(graph: nx.Graph) -> nx.Graph:
    fixed_graph = nx.DiGraph() if graph.is_directed() else nx.Graph()
    sorted_nodes = sorted(graph.nodes(data=True), key=lambda x: x[0])
    fixed_graph.add_nodes_from(sorted_nodes)
    edges = list(graph.edges(data=True))
    if not graph.is_directed():
        def _sort_source_target(edge):
            source, target, edge_data = edge
            if source > target:
                source, target = target, source
            return source, target, edge_data
        edges = [_sort_source_target(edge) for edge in edges]
    edges = sorted(edges, key=lambda x: f"{x[0]} -> {x[1]}")
    fixed_graph.add_edges_from(edges)
    return fixed_graph
```

源码注释解释得很直白：无向图里 `A→B` 和 `B→A` 等价，但 `graph.nodes()` 的**遍历顺序**会因插入顺序不同而变化，下游若依赖顺序就会出现不确定性。这里通过节点名排序 + 边端点排序 + 边键排序，把图规范化成唯一形态。

配合固定 seed，同一份图两次运行会得到**完全相同**的社区划分。这对 checkpoint 复用至关重要——见第六节。

`stable_largest_connected_component()` 把三件事串起来：

```python
def stable_largest_connected_component(graph: nx.Graph) -> nx.Graph:
    graph = graph.copy()
    graph = cast(nx.Graph, largest_connected_component(graph))
    graph = normalize_node_names(graph)   # html.unescape + upper + strip
    return _stabilize_graph(graph)
```

`normalize_node_names()` 会做 `html.unescape(node.upper().strip())`。注意这一步只影响**聚类内部使用的副本**（`graph.copy()`），原图节点名不变。

### 3.4 社区权重计算

`hierarchical_leiden` 返回的是 `(level, node, cluster)` 三元组序列，`run()` 把它重组成按层级分组的社区字典，并计算权重：

```python
for node_id, raw_community_id in node_id_to_community_map[level].items():
    if node_id not in nodes:
        logging.warning(f"Node {node_id} not found in the graph.")
        continue
    community_id = str(raw_community_id)
    if community_id not in result:
        result[community_id] = {"weight": 0, "nodes": []}
    result[community_id]["nodes"].append(node_id)
    result[community_id]["weight"] += (
        graph.nodes[node_id].get("rank", 0) * graph.nodes[node_id].get("weight", 1)
    )
```

权重公式：**社区权重 = Σ(节点 rank × 节点 weight)**

- `rank` 是节点度数，在 `CommunityReportsExtractor.__call__` 开头刚被刷新过；
- `weight` 是节点权重（抽取阶段写入，默认 1）。

然后做**归一化**：

```python
weights = [comm["weight"] for _, comm in result.items()]
if not weights:
    continue
max_weight = max(weights)
if max_weight == 0:
    continue
for _, comm in result.items():
    comm["weight"] /= max_weight
```

归一化后每层最重要的社区权重为 1.0，其余按比例落在 (0, 1]。这个值最终写进 community_report chunk 的 `weight_flt` 字段，检索时可用于排序加权。

两处 `continue` 是防御性的：空社区层或全零权重层直接跳过，避免除零。

### 3.5 node_id 缺失告警

`if node_id not in nodes` 这个检查看起来冗余（节点都来自同一张图），但因为 `normalize_node_names()` 做过大写化，如果原图存在**大小写不一致的同名节点**，聚类返回的节点名可能对不上原图。这个 warning 就是那种情况的哨兵。

## 四、社区报告生成

### 4.1 前置：刷新节点 rank

```python
async def __call__(self, graph, callback=None, task_id="", checkpoints=None, save_checkpoint=None):
    enable_timeout_assertion = os.environ.get("ENABLE_TIMEOUT_ASSERTION")
    for node_degree in graph.degree:
        graph.nodes[str(node_degree[0])]["rank"] = int(node_degree[1])

    communities: dict[str, dict[str, list]] = leiden.run(graph, {})
    total = sum([len(comm.items()) for _, comm in communities.items()])
```

`rank` 在 `graph_merge()` 里已经算过一次，这里再算是因为实体消解可能删除/合并了节点，度数已变。`total` 是**所有层级社区数之和**，用于进度回调。

### 4.2 单社区处理：extract_community_report()

每个社区一个 asyncio task，核心逻辑分五步。

**Step 1 — 跳过过小社区**

```python
cm_id, cm = community
weight = cm["weight"]
ents = cm["nodes"]
if len(ents) < 2:
    return
```

单节点社区没有内部关系可描述，直接跳过。注意这里 `return` 而非计入 `over`，所以进度分母 `total` 会略大于实际完成数——回调里可能看到 `Communities: 48/52` 这样"永不满格"的情况，属正常。

**Step 2 — checkpoint 回放**

```python
checkpoint_key = community_checkpoint_key(str(level), str(cm_id), list(ents))
checkpoint = checkpoints.get(checkpoint_key)
if isinstance(checkpoint, dict):
    response = checkpoint.get("structured_output")
    output = checkpoint.get("output")
    if isinstance(response, dict) and isinstance(output, str):
        add_community_info2graph(graph, response.get("entities", ents), response.get("title", ""))
        res_str.append(output)
        res_dict.append(response)
        over += 1
        if callback:
            callback(msg=f"Communities: {over}/{total}, used tokens: {token_count}")
        return
```

命中 checkpoint 则完全跳过 LLM 调用，直接把上次结果回填到图和结果列表。第六节详述 key 的构造。

**Step 3 — 构造实体表与关系表**

```python
ent_list = [{"entity": ent, "description": graph.nodes[ent]["description"]} for ent in ents]
ent_df = pd.DataFrame(ent_list)

rela_list = []
k = 0
for i in range(0, len(ents)):
    if k >= 10000:
        break
    for j in range(i + 1, len(ents)):
        if k >= 10000:
            break
        edge = graph.get_edge_data(ents[i], ents[j])
        if edge is None:
            continue
        rela_list.append({"source": ents[i], "target": ents[j], "description": edge["description"]})
        k += 1
rela_df = pd.DataFrame(rela_list)
```

用 pandas DataFrame 只是为了方便 `to_csv()`——最终喂给 LLM 的是 CSV 文本。

关系收集是 **O(n²)** 的两两枚举，用 `k >= 10000` 双重截断兜底。由于 `max_cluster_size=12`，正常社区最多 12 个节点、66 对组合，这个上限实际不会触发。它防的是 Leiden 在特殊拓扑下产出超大社区的极端情况。

**Step 4 — LLM 调用**

```python
prompt_variables = {
    "entity_df": ent_df.to_csv(index_label="id"),
    "relation_df": rela_df.to_csv(index_label="id"),
}
text = perform_variable_replacements(self._extraction_prompt, variables=prompt_variables)
async with chat_limiter:
    try:
        timeout = 180 if enable_timeout_assertion else 1000000000
        response = await asyncio.wait_for(
            self._async_chat(text, [{"role": "user", "content": "Output:"}], {}, task_id),
            timeout=timeout,
        )
    except asyncio.TimeoutError:
        logging.warning("extract_community_report._async_chat timeout, skipping...")
        return
    except Exception as e:
        logging.error(f"extract_community_report._async_chat failed: {e}")
        return
token_count += num_tokens_from_string(text + response)
```

三个细节：

- `index_label="id"` 让 CSV 首列变成 `id`，正好对上 prompt 里 grounding rules 要求的 `[Data: Entities (5), Relationships (37)]` 引用格式；
- `chat_limiter` 是全局共享的 asyncio 限流信号量，与实体抽取、实体消解共用同一个额度；
- 超时逻辑：只有设置了 `ENABLE_TIMEOUT_ASSERTION` 环境变量才真正启用 180 秒超时，否则用 `1000000000` 秒（约 31 年）等于不限时。这是刻意的——生产环境不想因为单个社区超时丢报告。

**失败即跳过**：超时或异常都是 `return`，不重试、不抛出。单个社区报告丢失不影响整体，代价是这一轮该社区没有报告，下次运行会重新尝试（因为没写 checkpoint）。

### 4.3 Step 5：响应解析与 checkpoint 落盘

LLM 返回的文本经常带 markdown 代码块包裹或前置说明，所以先做暴力裁剪，只保留最外层的 `{...}`：

```python
response = re.sub(r"^[^\{]*", "", response)
response = re.sub(r"[^\}]*$", "", response)
try:
    response = json.loads(response)
except json.JSONDecodeError as e:
    logging.error(f"Failed to parse JSON response: {e}")
    return

if not dict_has_keys_with_types(
    response,
    [
        ("title", str),
        ("summary", str),
        ("findings", list),
        ("rating", float),
        ("rating_explanation", str),
    ],
):
    return
```

`dict_has_keys_with_types` 做的是**类型级别**的校验，不只是检查 key 存在。任一字段类型不符就整条丢弃——宁可没有报告，也不要结构错乱的报告流入检索层。

校验通过后补上两个 LLM 不知道的字段，再写图和 checkpoint：

```python
response["weight"] = weight          # 来自 Leiden 归一化后的社区权重
response["entities"] = ents          # 社区成员实体列表
add_community_info2graph(graph, ents, response["title"])

output = self._get_text_output(response)
if save_checkpoint:
    await save_checkpoint(checkpoint_key, {"structured_output": response, "output": output})

res_str.append(output)
res_dict.append(response)
```

`add_community_info2graph()` 会把社区标题写回每个成员节点的 `communities` 列表（去重）。这一步让图节点反向持有社区归属，后续实体 chunk 落库时可以带上 `communities` 字段，检索时能从实体跳到社区报告。

`_get_text_output()` 把结构化 JSON 渲染成人类可读的 markdown 文本：

```python
def _get_text_output(self, parsed_output: dict) -> str:
    title = parsed_output.get("title", "Report")
    summary = parsed_output.get("summary", "")
    findings = parsed_output.get("findings", [])

    def finding_summary(finding: dict):
        if isinstance(finding, str):
            return finding
        return finding.get("summary")

    def finding_explanation(finding: dict):
        if isinstance(finding, str):
            return ""
        return finding.get("explanation")

    report_sections = "\n\n".join(
        f"## {finding_summary(f)}\n\n{finding_explanation(f)}" for f in findings
    )
    return f"# {title}\n\n{summary}\n\n{report_sections}"
```

注意 `findings` 元素同时兼容 `str` 和 `dict` 两种形态——LLM 有时会退化成返回纯字符串列表，这里做了容错而不是直接崩掉。

checkpoint 存的是 `{"structured_output": response, "output": output}` 双份数据。为什么不只存 JSON 然后回放时重新渲染文本？因为 `_get_text_output` 的实现可能变化,存两份保证回放结果与首次运行完全一致。

## 5. Prompt 设计分析

`COMMUNITY_REPORT_PROMPT` 是从 Microsoft GraphRAG 原版移植过来的,整体结构分四部分：

### 5.1 任务指令

```
You are an AI assistant that helps a human analyst to perform general information discovery.
Information discovery is the process of identifying and assessing relevant information associated with certain entities...
```

强调了三个目标：

1. **Comprehensiveness**：报告要全面覆盖社区内的所有实体和关系，不能遗漏重要信息；
2. **Relevance**：聚焦于与社区主题相关的信息，过滤掉无关细节；
3. **Specific, detailed, and grounded**：所有结论必须从输入的实体和关系表里找到依据，不能臆造。

### 5.2 输出格式要求

Prompt 通过 few-shot 示例明确了 JSON schema：

```json
{
  "title": "<report_title>",
  "summary": "<executive_summary>",
  "rating": <impact_severity_rating>,
  "rating_explanation": "<rating_explanation>",
  "findings": [
    {
      "summary": "<finding_summary>",
      "explanation": "<finding_explanation> [Data: Reports (report_ids)]"
    }
  ]
}
```

`rating` 是 0-10 的浮点数，表示该社区在整体语料中的"影响力/显著性"。实际用途有限（代码里只存不用），但保留下来是为了未来可能的社区排序或筛选。

### 5.3 Grounding 规则

Prompt 多次强调 `[Data: Entities (id1, id2, ...)]` 和 `[Data: Relationships (id1, id2, ...)]` 引用格式，要求 LLM 在每个 `explanation` 的最后附上数据出处。这是 GraphRAG 论文里"grounded generation"的核心——让 LLM 输出可验证、可溯源。

代码在构造 `entity_df` 和 `relation_df` 时用了 `index_label="id"`，就是为了生成带行号的 CSV，让 LLM 方便引用。

### 5.4 Few-shot 示例

Prompt 包含一个完整的输入-输出样例，展示了如何从 5 个实体、10 条关系生成一个包含 3 个 findings 的报告。示例的输入数据是虚构的，但格式和风格与真实场景一致，帮助 LLM 快速对齐输出规范。

### 5.5 max_report_length 参数

构造函数里 `self._max_report_length = max_report_length or 1500`，但实际 prompt 里并没有硬性字数限制的指令。这个参数在代码中**未被使用**——它存在于接口签名里，但不影响 LLM 调用。可能是历史遗留或预留未来的 token 裁剪逻辑。

## 6. Checkpoint 机制详解

### 6.1 checkpoint_key 的构造

每个社区报告的 checkpoint key 由三部分组成：

```python
def community_checkpoint_key(level: str, community_id: str, entities: list[str]) -> str:
    sorted_entities = sorted(entities)
    return f"{level}::{community_id}::{','.join(sorted_entities)}"
```

- `level`：Leiden 层次聚类的层级编号（0, 1, 2...）；
- `community_id`：该层内的社区 ID；
- `sorted_entities`：社区成员实体列表，排序后拼接。

为什么要把实体列表也放进 key？因为社区成员可能因为图的变化（新增实体、实体消解）而改变。如果只用 `level::community_id`，回放时无法检测到"同一个 ID 但成员已变"的情况，会错误复用旧报告。

### 6.2 Checkpoint 复用的时机

`extract_community_report` 开头先查 checkpoint：

```python
checkpoint_key = community_checkpoint_key(str(level), str(cm_id), list(ents))
checkpoint = checkpoints.get(checkpoint_key)
if isinstance(checkpoint, dict):
    response = checkpoint.get("structured_output")
    output = checkpoint.get("output")
    if isinstance(response, dict) and isinstance(output, str):
        add_community_info2graph(graph, response.get("entities", ents), response.get("title", ""))
        res_str.append(output)
        res_dict.append(response)
        return
```

命中 checkpoint 后直接 `return`，跳过 LLM 调用。这是社区检测阶段**最大的成本节约点**——GraphRAG 的社区结构通常在几轮迭代后趋于稳定，大部分社区报告可以复用，只有新增或变化的社区才需要重新生成。

### 6.3 Cleanup 时机

`extract_community` 的最后一步是清理 checkpoint：

```python
await cleanup_checkpoints(tenant_id, kb_id, COMMUNITY_CHECKPOINT)
```

为什么要删？因为社区检测是**全量重跑**的——每次都从完整的图重新聚类，旧的社区 ID 和新的社区 ID 之间没有稳定的对应关系。保留旧 checkpoint 会导致 key 空间膨胀，且命中率极低（只有成员列表完全相同才能复用）。

删除策略是**成功后删**，如果中途失败（异常或超时），checkpoint 会保留到下次运行，起到断点续传的作用。

## 7. Community chunk 持久化

### 7.1 chunk 结构

每个社区报告落成一条 chunk，字段构造在 `index.py:937-967`：

```python
for stru, rep in zip(community_structure, community_reports):
    obj = {
        "report": rep,
        "evidences": "\n".join([f.get("explanation", "") for f in stru["findings"]]),
    }
    chunk_payload_for_id = {
        "content_with_weight": f"community_report::{stru['title']}",
        "kb_id": kb_id,
    }
    chunk = {
        "id": chunk_id(chunk_payload_for_id),
        "docnm_kwd": stru["title"],
        "title_tks": rag_tokenizer.tokenize(stru["title"]),
        "content_with_weight": json.dumps(obj, ensure_ascii=False),
        "content_ltks": rag_tokenizer.tokenize(obj["report"] + " " + obj["evidences"]),
        "knowledge_graph_kwd": "community_report",
        "weight_flt": stru["weight"],
        "entities_kwd": stru["entities"],
        "important_kwd": stru["entities"],
        "kb_id": kb_id,
        "source_id": list(doc_ids),
        "available_int": 0,
    }
    chunk["content_sm_ltks"] = rag_tokenizer.fine_grained_tokenize(chunk["content_ltks"])
```

几个关键字段的用途：

| 字段 | 值 | 检索意义 |
|---|---|---|
| `knowledge_graph_kwd` | `"community_report"` | 类型标记，检索层用它区分 entity / relation / community_report 三类 chunk |
| `docnm_kwd` | 社区标题 | 展示用的"文档名"，让报告在结果列表里有可读标识 |
| `content_with_weight` | `{"report": ..., "evidences": ...}` 的 JSON | 实际内容，report 是渲染后的 markdown，evidences 是所有 findings 的 explanation 拼接 |
| `weight_flt` | Leiden 归一化权重 | 可用于排序，权重高的社区更重要 |
| `entities_kwd` / `important_kwd` | 社区成员实体列表 | 支持从实体名反查所属社区报告 |
| `source_id` | `graph.graph["source_id"]` | 该 KB 下所有贡献过图数据的文档 ID，社区报告是跨文档产物，所以挂全量 |
| `available_int` | `0` | 标记为不可直接命中普通检索，只在 GraphRAG 专用检索路径中使用 |

`content_ltks` 和 `content_sm_ltks` 是分词后的检索字段，粗粒度 + 细粒度双写是 RAGFlow 全局的检索约定。

### 7.2 确定性 chunk ID

`chunk_id()` 的输入只有 `kb_id` 和 `community_report::{title}`，**不包含报告内容**。这意味着：

- 同一个 KB 下、同名社区的报告，多次运行得到相同的 chunk ID；
- 报告内容变了但标题没变，会**原地覆盖**而不是产生新行。

这是刻意设计，配合下面的 insert-then-prune 模式使用。代码注释里写得很清楚：

> Deterministic id derived from (kb_id, community title) so reruns of extract_community produce stable ids.

副作用是：如果两个不同的社区被 LLM 起了同名标题，它们会互相覆盖。实践中标题由 LLM 根据社区内容生成，重名概率低，但不为零。

### 7.3 Insert-then-prune 模式

这是本阶段最值得注意的工程细节。先看代码顺序：

```python
new_ids: set[str] = {c["id"] for c in chunks}

# 1. 快照现有 ID
old_ids: list[str] = []
try:
    existing_res = await thread_pool_exec(
        settings.docStoreConn.search,
        ["id"], [], {"knowledge_graph_kwd": ["community_report"]}, [],
        OrderByExpr(), 0, 10000,
        search.index_name(tenant_id), [kb_id],
    )
    existing_fields = settings.docStoreConn.get_fields(existing_res, ["id"])
    old_ids = list(existing_fields.keys())
except Exception:
    logging.exception("Failed to enumerate existing community reports ...")
    await thread_pool_exec(settings.docStoreConn.delete,
        {"knowledge_graph_kwd": "community_report", "kb_id": kb_id},
        search.index_name(tenant_id), kb_id)
    old_ids = []

# 2. 插入新数据
await insert_chunks_bounded(chunks, tenant_id, kb_id, callback=callback, label="Insert community reports")

# 3. 删除陈旧数据
stale_ids = [i for i in old_ids if i not in new_ids]
if stale_ids:
    try:
        await thread_pool_exec(settings.docStoreConn.delete,
            {"knowledge_graph_kwd": ["community_report"], "id": stale_ids},
            search.index_name(tenant_id), kb_id)
    except Exception:
        logging.exception("Failed to prune %d stale community reports ...", len(stale_ids))
```

**为什么不用 delete-then-insert？** 假设先删全部再插入，如果插入过程中崩溃（进程被杀、ES 不可用），KB 里就一条社区报告都不剩——检索直接退化。而 insert-then-prune 的失败态是"新旧混存"，检索仍然可用，只是可能返回过期报告。可用性优先于一致性。

三处容错的层次也很清楚：

- **快照失败** → 退回 delete-everything-then-insert（旧行为），因为不知道哪些是陈旧的，只能全删重建；
- **插入失败** → `insert_chunks_bounded` 内部的异常会向上抛，此时旧数据还在，KB 保持上一轮的完整状态；
- **prune 失败** → 只记日志不抛出，新数据已就位，残留陈旧行属于可接受的降级。

`10000` 是 search 的 size 上限。如果单个 KB 的社区报告超过 10000 条，快照会不完整，导致部分陈旧行永远不被清理。这是一个已知的规模上限。

## 9. 关键配置参数

| 参数 | 位置 | 默认值 | 说明 |
|---|---|---|---|
| `timeout` | `@timeout(60 * 30, 1)` | 1800s (30min) | 整个 extract_community 的超时时间，超时后重试 1 次 |

| `LLM timeout` | `asyncio.wait_for()` | `180s` / `1000000000s` | 单个社区报告的 LLM 调用超时，取决于 `ENABLE_TIMEOUT_ASSERTION` 环境变量 |

| `COMMUNITY_CHECKPOINT` | `checkpoints.py` | `"graphrag_checkpoint_community"` | Redis checkpoint 前缀 |

环境变量：

- `ENABLE_TIMEOUT_ASSERTION`：设置后启用 180s LLM 超时，未设置时几乎不限时（10 亿秒）。生产环境通常不设，避免丢失报告。

## 10. 性能优化点

### 10.1 并行处理

所有社区报告生成是并行的：

```python
tasks = []
for level, comm in communities.items():
    for community in comm.items():
        tasks.append(asyncio.create_task(extract_community_report(level, community)))
await asyncio.gather(*tasks, return_exceptions=False)
```

假设 Leiden 聚类出 50 个社区，50 个 LLM 请求会同时发出（受 `chat_limiter` 信号量限制实际并发数）。这是社区检测能在合理时间内完成的关键。

### 10.2 Checkpoint 复用

命中 checkpoint 的社区直接跳过 LLM 调用，节省成本和时间。实践中图结构稳定后，90%+ 的社区可以复用。

### 10.3 权重归一化

Leiden 返回的权重会归一到 [0, 1]，避免权重数值范围随图规模膨胀，保持可比性。

### 10.4 边数限制

单社区最多取 10000 条边，避免超大社区（几百个实体、几千条关系）导致 LLM prompt 超长或内存溢出。实际场景中极少碰到上限。

### 10.5 图稳定化

`_stabilize_graph()` 确保同一图多次运行聚类结果一致，配合 `seed=0xDEADBEEF` 让 checkpoint key 能稳定命中。

## 11. 错误处理与容错

### 11.1 超时跳过

单个社区 LLM 超时或异常，只记日志并 `return`，不影响其他社区。最终可能有部分社区没有报告，但不会导致整个任务失败。

### 11.2 JSON 解析失败

LLM 返回格式错误时，正则裁剪 + `dict_has_keys_with_types` 双重保护。不符合 schema 的响应直接丢弃，不会流入检索层。

### 11.3 小社区过滤

成员 < 2 的社区没有分析价值，直接跳过节省 LLM 调用。

### 11.4 任务取消检查

`extract_community` 在多个关键点调用 `_has_cancel_and_exit(task_id, ...)`，支持用户主动取消长耗时任务。

### 11.5 Insert-then-prune 容错

如前所述，快照失败退回全删、插入失败保留旧数据、prune 失败只记日志，三层容错保证检索可用性。

### 11.6 Checkpoint 保留

`cleanup_checkpoints` 只在整个流程成功后执行。如果中途崩溃，checkpoint 会保留，下次运行可以从断点续传。

---

## 总结

社区检测与报告阶段是 GraphRAG 中 LLM 调用成本最高、最依赖并行和容错的模块。核心机制是：

1. **Leiden 层次聚类** - 图稳定化 + 确定性种子保证可复现；
2. **并行 LLM 生成** - asyncio.gather 实现社区级并行；
3. **Checkpoint 复用** - 图稳定后大部分社区可跳过 LLM；
4. **Insert-then-prune** - 可用性优先的持久化模式；
5. **多层容错** - 单社区失败不影响整体，checkpoint 支持断点续传。

配合前面的实体消解和后续的检索模块，社区报告为 RAGFlow 提供了"高层语义摘要"检索能力——用户查询时不只匹配单个实体/关系，还能命中整个主题社区的综合报告。

# 09 - 容错与性能设计

## 问题陈述

GraphRAG 的知识图谱构建是一个多阶段、高延迟、资源密集的流程，涉及大量 LLM 调用、向量嵌入计算和数据库写入。系统需要在以下约束下保证稳定性和效率：

1. **超时控制**：单个 LLM 调用可能因模型负载或网络问题超时，需要设置合理的超时阈值并优雅降级
2. **并发限流**：大规模文档集可能触发数千次并发调用，需要限制并发度以避免服务过载
3. **重试机制**：临时性故障（网络抖动、数据库锁竞争）需要可配置的重试和退避策略
4. **缓存复用**：LLM 响应和向量嵌入计算成本高，必须利用缓存避免重复计算
5. **断点续传**：长时间运行的任务可能被中断，需要支持从已完成的阶段恢复
6. **批量优化**：向量化、数据库插入等操作需要批量处理以均摊固定开销
7. **进度跟踪**：用户需要实时了解任务进度，任务取消时需要及时清理资源

本文档将从超时控制、并发管理、缓存策略、批量处理、断点续传和进度管理六个维度，剖析 RAGFlow 的容错与性能实现。

## 1. 超时控制机制

### 1.1 超时装饰器层次

RAGFlow 使用 `@timeout` 装饰器为不同阶段设置超时限制，超时阈值根据任务复杂度分级：

| 阶段 | 超时时长 | 代码位置 | 原因 |
|------|---------|---------|------|
| 文档分块 | 80 分钟 | `task_executor.py:@timeout(60*80)` | 大文档 OCR 解析耗时长 |
| 单文档上传 | 60 秒 | `task_executor.py:@timeout(60)` | 网络传输和存储写入 |
| 批量向量编码 | 60 秒 | `task_executor.py:@timeout(60)` | 单批次嵌入调用 |
| RAPTOR 聚类 | 60 分钟 | `task_executor.py:@timeout(3600)` | 递归摘要涉及多轮 LLM |
| 任务总处理 | 3 小时 | `task_executor.py:@timeout(60*60*3)` | 单任务生命周期上限 |

分级设计的核心思想是**内层超时短、外层超时长**：内层的单次调用快速失败，让重试机制有机会介入；外层的总超时兜底，防止任务无限挂起占用 worker。

### 1.2 可切换的超时断言模式

`insert_chunks_bounded` 中引入了 `ENABLE_TIMEOUT_ASSERTION` 环境变量，用于在测试环境中主动触发超时：

```python
enable_timeout_assertion = os.environ.get("ENABLE_TIMEOUT_ASSERTION")
...
timeout_s = 3 if enable_timeout_assertion else 30000000
```

这是一个**测试友好的设计**：
- 生产环境下 `timeout_s = 30000000`（约 347 天），实际等价于「不超时」，因为外层已有 3 小时的任务级超时
- 测试环境下设为 3 秒，可以快速验证超时分支和重试逻辑是否正确
- 避免了为测试超时行为而引入 mock 或 monkeypatch 的复杂性

这种做法的取舍是：写入层不做独立超时保护，完全依赖外层任务超时。合理性在于数据库写入本身有连接级超时，且写入失败会抛异常而非静默挂起。

## 2. 并发限流机制

### 2.1 信号量分层

RAGFlow 为不同资源类型设置独立的信号量，避免单一资源成为全局瓶颈：

```python
chat_limiter = LoopLocalSemaphore(int(os.environ.get("MAX_CONCURRENT_CHATS", 10)))
```

`graphrag/utils.py:42` 定义的 `chat_limiter` 是 GraphRAG 中最关键的限流器。所有 LLM 调用（实体抽取、实体消解、社区报告生成）都必须先获取该信号量。

主要限流器一览：

| 限流器 | 作用域 | 默认值 | 环境变量 |
|--------|--------|--------|---------|
| `chat_limiter` | LLM 对话调用 | 10 | `MAX_CONCURRENT_CHATS` |
| `chunk_limiter` | 文档分块 | - | `MAX_CONCURRENT_CHUNK_BUILDERS` |
| `embed_limiter` | 向量嵌入 | - | - |
| `minio_limiter` | 对象存储 IO | - | `MAX_CONCURRENT_MINIO` |
| `kg_limiter` | 知识图谱构建 | - | - |

### 2.2 LoopLocalSemaphore 的必要性

`chat_limiter` 使用的是 `LoopLocalSemaphore` 而非标准 `asyncio.Semaphore`。原因在于 `asyncio.Semaphore` 在创建时会绑定到当前事件循环，而 RAGFlow 的 task executor 在不同 worker 中可能创建多个事件循环。若模块级的信号量绑定到了已关闭的循环，后续 `acquire()` 会抛出 `RuntimeError: got Future attached to a different loop`。

`LoopLocalSemaphore` 通过为每个事件循环维护独立的信号量实例来规避这个问题，使得模块级全局限流器可以安全地跨循环使用。

### 2.3 写入并发的独立控制

图谱写入使用独立的信号量，与 LLM 限流解耦：

```python
_INSERT_BULK_SIZE = max(1, int(os.environ.get("GRAPHRAG_INSERT_BULK_SIZE", 64)))
_INSERT_CONCURRENCY = max(1, int(os.environ.get("GRAPHRAG_INSERT_CONCURRENCY", 4)))
```

`graphrag/utils.py:49-50` 定义了两个关键参数：
- `_INSERT_BULK_SIZE = 64`：每批插入 64 个 chunk
- `_INSERT_CONCURRENCY = 4`：最多 4 个批次并发写入

两个 `max(1, ...)` 的包装保证了即使环境变量被误设为 0 或负数，也不会导致除零或死锁。

并发度选择 4 而非更高值的考量：搜索引擎（Elasticsearch/Infinity）的写入是 CPU 和 IO 双密集操作，过高并发会引发写入队列积压和拒绝（`es_rejected_execution_exception`）。4 是在吞吐和稳定性间的经验平衡点。

## 3. 重试与退避策略

### 3.1 insert_chunks_bounded 的重试实现

图谱 chunk 写入是整个流程的最后一环，失败会导致前面所有 LLM 计算白费，因此实现了显式的重试逻辑：

```python
async def insert_chunks_bounded(chunks, tenant_id, kb_id, *, callback=None, label="Insert chunks"):
    enable_timeout_assertion = os.environ.get("ENABLE_TIMEOUT_ASSERTION")
    sem = asyncio.Semaphore(_INSERT_CONCURRENCY)
    max_retries = 3

    async def _insert_batch(batch, batch_idx):
        async with sem:
            timeout_s = 3 if enable_timeout_assertion else 30000000
            for attempt in range(max_retries):
                try:
                    result = await asyncio.wait_for(
                        trio.to_thread.run_sync(lambda: settings.docStoreConn.insert(batch, ...)),
                        timeout=timeout_s,
                    )
                    return result
                except asyncio.TimeoutError:
                    if attempt < max_retries - 1:
                        wait = 2**attempt
                        await asyncio.sleep(wait)
                    else:
                        raise
```

关键设计点：

1. **指数退避**：等待时间为 `2^attempt` 秒，即 1s → 2s → 失败。总等待 3 秒，不会显著延长任务时间，但足以跨过短暂的写入队列拥塞
2. **信号量在重试外层**：`async with sem` 包裹整个重试循环，重试期间仍占用并发槽位。这是有意为之——如果释放槽位，重试请求会与新请求竞争，可能加剧拥塞
3. **最后一次不等待**：`attempt < max_retries - 1` 判断避免最后一次失败后的无意义等待
4. **同步调用线程化**：`trio.to_thread.run_sync` 将阻塞的数据库写入移出事件循环，防止阻塞其他协程

### 3.2 LLM 调用的隐式重试

LLM 调用层（`chat` 函数）内部已集成重试逻辑，包括：
- 速率限制错误（`RateLimitError`）：自动退避重试
- 超时错误：单次调用超时后抛出，由外层 `@timeout` 装饰器决定是否中断任务
- 模型故障：部分 LLM SDK 会自动切换备用端点

GraphRAG 代码不需要为每个 `chat()` 调用显式包装重试，重试逻辑下沉到 LLM 适配层。这简化了上层代码，但也意味着 LLM 调用的实际耗时不可预测——一次成功的调用可能内部重试了多次。

### 3.3 为何不重试图谱合并操作

`graph_merge` 和 `set_graph` 等图操作没有重试逻辑。原因有二：

1. **幂等性保证难度高**：图合并涉及属性拼接（`description += GRAPH_FIELD_SEP + ...`），重复执行会导致字段重复累加
2. **错误不可恢复**：图操作的异常通常来自内存溢出或数据结构损坏，重试无法解决根因，应直接失败并暴露问题

## 4. 缓存策略

### 4.1 LLM 响应缓存

LLM 调用是 GraphRAG 最昂贵的操作，缓存设计决定了重跑任务的成本：

```python
def get_llm_cache(llmnm, txt, history, genconf):
    hasher = xxhash.xxh64()
    hasher.update((str(llmnm) + str(txt) + str(history) + str(genconf)).encode("utf-8"))
    k = hasher.hexdigest()
    bin = REDIS_CONN.get(k)
    return bin if bin else None

def set_llm_cache(llmnm, txt, v, history, genconf):
    hasher = xxhash.xxh64()
    hasher.update((str(llmnm) + str(txt) + str(history) + str(genconf)).encode("utf-8"))
    k = hasher.hexdigest()
    REDIS_CONN.set(k, v.encode("utf-8"), 24 * 3600)
```

`graphrag/utils.py:170-188` 实现了基于内容的缓存键生成。关键设计：

1. **哈希算法选择**：使用 xxHash 而非 MD5/SHA 是性能考量，xxHash 在长字符串上比 MD5 快 5-10 倍，且 64 位输出空间（2^64）足以避免碰撞
2. **缓存键组成**：`(model_name, text, history, generation_config)` 四元组，缺一不可。省略任何一项都会导致不同上下文的调用错误命中
3. **TTL 设置**：24 小时过期，与典型 GraphRAG 任务完成时间（数小时）匹配。过长会占用 Redis 内存，过短则无法覆盖任务重跑场景
4. **编码细节**：响应文本编码为 UTF-8 存储，读取时隐式解码。若响应包含 JSON，调用方负责反序列化

### 4.2 向量嵌入缓存

嵌入缓存与 LLM 缓存结构相似，但键生成更简单：

```python
def get_embed_cache(llmnm, txt):
    hasher = xxhash.xxh64()
    hasher.update(str(llmnm).encode("utf-8"))
    hasher.update(str(txt).encode("utf-8"))
    k = hasher.hexdigest()
    bin = REDIS_CONN.get(k)
    if not bin:
        return
    return np.array(json.loads(bin))

def set_embed_cache(llmnm, txt, arr):
    hasher = xxhash.xxh64()
    hasher.update(str(llmnm).encode("utf-8"))
    hasher.update(str(txt).encode("utf-8"))
    k = hasher.hexdigest()
    arr = json.dumps(arr.tolist() if isinstance(arr, np.ndarray) else arr)
    REDIS_CONN.set(k, arr.encode("utf-8"), 24 * 3600)
```

与 LLM 缓存的差异：

- **分次 update**：`hasher.update()` 分两次调用而非拼接字符串，避免了模型名与文本边界模糊导致的碰撞。例如 `("modelA", "Btext")` 和 `("modelAB", "text")` 在拼接方案下会产生相同哈希，而分次 update 因为内部状态不同而区分开
- **类型归一化**：`arr.tolist() if isinstance(arr, np.ndarray) else arr` 兼容 numpy 数组和普通 list 两种输入，写入时统一为 JSON 数组
- **读取时重建 ndarray**：`np.array(json.loads(bin))` 保证调用方拿到的类型与未命中缓存时一致，避免类型分支

### 4.3 批量缓存探测优化

单条 `REDIS_CONN.get()` 在异步上下文中会阻塞事件循环。为此引入了批量探测：

```python
def _batch_embed_cache_misses(llmnm: str, keys: list) -> "list[bool]":
    """Return a boolean miss-mask for *keys* using a single MGET round-trip."""
    if not keys:
        return []
    hashes = []
    for key in keys:
        h = xxhash.xxh64()
        h.update(str(llmnm).encode("utf-8"))
        h.update(str(key).encode("utf-8"))
        hashes.append(h.hexdigest())
    return [v is None for v in REDIS_CONN.mget(hashes)]
```

这个函数返回一个布尔掩码，标记哪些 key 未命中缓存。设计价值：

1. **单次往返**：`MGET` 将 N 次网络往返压缩为 1 次。在 1000 个 chunk 的场景下，假设单次 Redis RTT 为 0.5ms，从 500ms 降至 0.5ms
2. **不返回值只返回掩码**：调用方只需知道「哪些需要重新计算」，实际值的读取延后到批量嵌入之后。这避免了在掩码计算阶段就反序列化所有命中的向量（可能是数百 MB 的 JSON）
3. **与写入配对**：`_write_embed_cache_batch` 通过 `thread_pool_exec` 将同步 SET 调用移出事件循环，与 `_batch_embed_cache_misses` 形成读写对称

```python
def _write_embed_cache_batch(llmnm: str, keys: list, embeddings) -> None:
    for key, ebd in zip(keys, embeddings):
        set_embed_cache(llmnm, key, ebd)
```

### 4.4 标签缓存的短 TTL

标签数据使用 600 秒（10 分钟）的短 TTL：

```python
def set_tags_to_cache(kb_ids, tags):
    hasher = xxhash.xxh64()
    hasher.update(str(kb_ids).encode("utf-8"))
    k = hasher.hexdigest()
    REDIS_CONN.set(k, json.dumps(tags).encode("utf-8"), 600)
```

TTL 从 24 小时降到 10 分钟的原因是**数据新鲜度要求不同**：标签集合会随着新文档入库而变化，若缓存 24 小时，用户新增文档后的标签筛选结果会长时间不更新。10 分钟是「可接受的延迟」与「减少重复查询」的折中。

## 5. 断点续传机制

### 5.1 两层恢复设计

GraphRAG 的恢复机制分为两个粒度：

| 层级 | 实现 | 粒度 | 存储位置 |
|------|------|------|---------|
| 阶段标记 | `phase_markers.py` | 整个阶段（消解/社区） | `graphrag:phase:{kb_id}:{phase}` |
| 检查点 | `checkpoints.py` | 单个社区/单批实体对 | `graphrag:checkpoint:{tenant}:{kb}:{type}:{key}` |

粗粒度的阶段标记用于跳过整个已完成的阶段；细粒度的检查点用于在阶段内部跳过已计算的单元。

### 5.2 阶段标记实现

`phase_markers.py` 定义了两个阶段标记：

```python
PHASE_RESOLUTION = "resolution_done"
PHASE_COMMUNITY = "community_done"

def has_phase_marker(kb_id: str, phase: str) -> bool:
    if not kb_id or not phase:
        return False
    try:
        return bool(REDIS_CONN.exist(_phase_key(kb_id, phase)))
    except Exception:
        logging.exception("has_phase_marker(%s, %s) failed", kb_id, phase)
        return False
```

异常处理策略是**静默降级**：Redis 故障时返回 `False`，让任务重新执行该阶段。注释中明确说明：「Markers are an optimization; a Redis miss must NEVER block a run.」这是一个关键的容错决策——宁可重复计算，也不能因为标记查询失败而阻塞任务。

标记的生命周期管理：

```python
def set_phase_marker(kb_id: str, phase: str, ttl: int = 7 * 24 * 3600) -> bool:
    return bool(REDIS_CONN.set(_phase_key(kb_id, phase), "1", ttl))

def clear_phase_markers(kb_id: str, phases: tuple[str, ...] = ALL_PHASES) -> None:
    for phase in phases:
        try:
            REDIS_CONN.delete(_phase_key(kb_id, phase))
        except Exception:
            logging.exception("clear_phase_markers(%s, %s) failed", kb_id, phase)
```

关键设计点：

1. **7 天 TTL**：注释解释「7 days is well above any expected single GraphRAG run on typical hardware and keeps stale markers self-pruning」。即使无效化路径遗漏，标记也会自动过期，避免永久性错误
2. **无效化时机**：调用方负责在两种情况下清除标记——新文档合并进全局图时（导致消解和社区结果失效）、用户手动清空图谱时
3. **KB 范围而非 Task 范围**：标记绑定到知识库而非单次任务，使得任务取消后重启仍能利用已完成的工作。这是有意为之，因为消解和社区结果只依赖图结构而非任务上下文

### 5.3 检查点机制

检查点用于更细粒度的恢复，典型场景是社区报告生成（可能涉及数千个社区）：

```python
COMMUNITY_CHECKPOINT = "graphrag_checkpoint_community"
RESOLUTION_CHECKPOINT = "graphrag_checkpoint_resolution"
CHECKPOINT_TTL_SECONDS = 7 * 24 * 3600

def community_checkpoint_key(level: str, community_id: str, nodes: list[str]) -> str:
    return stable_checkpoint_key("community", str(level), str(community_id), sorted(nodes))

def resolution_checkpoint_key(entity_type: str, pairs: list[tuple[str, str]]) -> str:
    normalized_pairs = sorted([sorted([a, b]) for a, b in pairs])
    return stable_checkpoint_key("resolution", entity_type, normalized_pairs)
```

检查点键生成使用 SHA-256 而非 xxHash，原因是键需要**内容寻址的稳定性**：
- 同样的社区节点集合必须生成完全相同的键，以便跨任务复用
- SHA-256 的确定性保证了排序后的输入 `sorted(nodes)` 产生唯一映射
- xxHash 的优势在速度，但检查点键生成频率远低于缓存键（数千次 vs 数百万次），速度差异不敏感

检查点存储结构：

```python
def _checkpoint_index_key(tenant_id: str, kb_id: str, checkpoint_type: str) -> str:
    return f"graphrag:checkpoint:{tenant_id}:{kb_id}:{checkpoint_type}:keys"

def _checkpoint_data_key(tenant_id: str, kb_id: str, checkpoint_type: str, checkpoint_key: str) -> str:
    return f"graphrag:checkpoint:{tenant_id}:{kb_id}:{checkpoint_type}:{checkpoint_key}"
```

采用了**索引 + 数据分离**的设计：
- `keys` 集合存储所有检查点键的列表
- 每个检查点键指向独立的数据条目

这种设计支持高效的「加载所有检查点」操作，用于任务启动时的恢复阶段。

### 5.4 SSCAN 分页遍历

加载检查点时不使用 `SMEMBERS` 而使用 `SSCAN` 分页：

```python
CHECKPOINT_PAGE_SIZE = 1000

def _iter_checkpoint_keys(index_key: str, page_size: int | None):
    redis_client = getattr(REDIS_CONN, "REDIS", None)
    if redis_client is None or not hasattr(redis_client, "sscan_iter"):
        raise RuntimeError("Redis SSCAN is unavailable for GraphRAG checkpoint index iteration")
    return redis_client.sscan_iter(index_key, count=_checkpoint_page_size(page_size))
```

原因是 `SMEMBERS` 在大集合上会阻塞 Redis 单线程数千毫秒，影响整个实例的所有客户端。`SSCAN` 以 1000 为页大小增量遍历，每次调用只阻塞微秒级时间。

`getattr` 和 `hasattr` 的防御性检查处理了 Redis 连接封装可能不暴露底层客户端的情况，此时抛出明确错误而非静默失败。

### 5.5 两级异常隔离

检查点加载的异常处理有两个层级：

```python
def _load_checkpoints_sync(tenant_id, kb_id, checkpoint_type, page_size) -> dict[str, Any]:
    checkpoints: dict[str, Any] = {}
    index_key = _checkpoint_index_key(tenant_id, kb_id, checkpoint_type)
    try:
        checkpoint_keys = _iter_checkpoint_keys(index_key, page_size)
    except Exception:
        logging.exception("Failed to load GraphRAG checkpoint index type=%s kb=%s", checkpoint_type, kb_id)
        return checkpoints

    for checkpoint_key in checkpoint_keys:
        checkpoint_key = _decode_redis_value(checkpoint_key)
        try:
            value = REDIS_CONN.get(_checkpoint_data_key(...))
            value = _decode_redis_value(value)
            if not value:
                continue
            checkpoints[checkpoint_key] = json.loads(value)
        except Exception:
            logging.exception("Failed to parse GraphRAG checkpoint type=%s kb=%s key=%s", ...)
    return checkpoints
```

- **索引层失败**：直接返回空字典，等价于「无检查点」，任务从头执行
- **单条数据失败**：跳过该条继续处理其他条目，最大化利用可用检查点

这种设计保证了**部分损坏的检查点不会导致全部恢复能力丧失**。若某个社区的检查点 JSON 格式损坏（例如写入时进程被 kill），只影响该社区重新计算。

### 5.6 检查点写入的原子性

写入使用 Redis pipeline 事务：

```python
async def save_checkpoint(tenant_id, kb_id, checkpoint_type, checkpoint_key, payload) -> bool:
    index_key = _checkpoint_index_key(tenant_id, kb_id, checkpoint_type)
    data_key = _checkpoint_data_key(tenant_id, kb_id, checkpoint_type, checkpoint_key)
    try:
        redis_client = getattr(REDIS_CONN, "REDIS", None)
        if redis_client is None or not hasattr(redis_client, "pipeline"):
            logging.warning("GraphRAG checkpoint Redis client unavailable ...")
            return False
        pipeline = redis_client.pipeline(transaction=True)
        pipeline.set(data_key, json.dumps(payload, ensure_ascii=False), ex=CHECKPOINT_TTL_SECONDS)
        pipeline.sadd(index_key, checkpoint_key)
        pipeline.expire(index_key, CHECKPOINT_TTL_SECONDS)
        pipeline.execute()
        return True
    except Exception:
        logging.exception("Failed to save GraphRAG checkpoint ...")
        return False
```

三个操作必须原子执行：

1. `SET data_key`：写入检查点数据
2. `SADD index_key`：将键加入索引集合
3. `EXPIRE index_key`：刷新索引的 TTL

若 1 成功而 2 失败，数据成为孤儿（永远不会被加载，但占用内存直到 TTL 过期）；若 2 成功而 1 失败，索引中的键指向不存在的数据（加载时被 `if not value: continue` 跳过）。事务保证两者一致。

`ensure_ascii=False` 保证中文实体名不被转义为 `\uXXXX`，减少存储体积约 40%。

`return False` 而非抛异常的设计意味着**检查点保存失败不影响主流程**——最坏情况是下次重跑时重复计算该单元。

## 6. 批量处理优化

### 6.1 批量参数一览

| 参数 | 值 | 作用 | 配置方式 |
|------|-----|------|---------|
| `_INSERT_BULK_SIZE` | 64 | 图谱 chunk 批量插入大小 | `GRAPHRAG_INSERT_BULK_SIZE` |
| `_INSERT_CONCURRENCY` | 4 | 图谱插入并发批次数 | `GRAPHRAG_INSERT_CONCURRENCY` |
| `BATCH_SIZE` | 64 | 通用文档 chunk 批量大小 | 常量 |
| `EMBEDDING_BATCH_SIZE` | - | 嵌入模型单次调用文本数 | `settings` |
| `DOC_BULK_SIZE` | - | 文档存储批量写入大小 | `settings` |
| `CHECKPOINT_PAGE_SIZE` | 1000 | SSCAN 分页大小 | 常量 |

### 6.2 批量大小的权衡

64 这个数值在多处出现，其选择依据：

- **过小（如 8）**：网络往返和请求头开销占比高，吞吐低
- **过大（如 512）**：单个请求体积大（每个 entity chunk 含 1024 维向量约 8KB，512 个约 4MB），容易触发搜索引擎的 `http.max_content_length` 限制，且单次失败的重试成本高
- **64 的实际效果**：单批约 512KB，在大多数搜索引擎的默认限制内，重试成本可控

### 6.3 缓存预热的批量化

`set_graph` 阶段会先批量探测嵌入缓存，再只对未命中的文本调用嵌入模型：

1. 收集所有待嵌入的 entity/relation 描述文本
2. 调用 `_batch_embed_cache_misses` 获得掩码（1 次 Redis MGET）
3. 对掩码为 `True` 的文本批量调用嵌入模型
4. 调用 `_write_embed_cache_batch` 批量回写缓存（通过线程池）

在增量更新场景下（新增少量文档），大部分实体描述已在缓存中，这个流程可以将嵌入调用量减少 80% 以上。

## 7. 进度跟踪与任务取消

### 7.1 set_progress：进度更新与取消检测的统一入口

`task_executor.py:213` 的 `set_progress` 函数是所有任务进度管理的中心：

```python
def set_progress(task_id, from_page=0, to_page=-1, prog=None, msg="Processing..."):
    try:
        if prog is not None and prog < 0:
            msg = "[ERROR]" + msg
        cancel = has_canceled(task_id)  # 第217行：每次进度更新都检查取消标记
        
        if cancel:
            msg += " [Canceled]"
            prog = -1
        
        if to_page > 0:
            if msg:
                if from_page < to_page:
                    msg = f"Page({from_page + 1}~{to_page}): " + msg
        if msg:
            msg = datetime.now().strftime("%H:%M:%S") + " " + msg  # 添加时间戳
        
        d = {"progress_msg": msg}
        if prog is not None:
            d["progress"] = prog
        
        TaskService.update_progress(task_id, d)  # 更新数据库
        
        close_connection()
        if cancel:
            raise TaskCanceledException(msg)  # 第237行：检测到取消后立即抛异常
        logging.info(f"set_progress({task_id}), progress: {prog}, progress_msg: {msg}")
    except TaskCanceledException:
        raise  # 重新抛出，让调用栈展开
    except DoesNotExist:
        logging.warning(f"set_progress({task_id}) got exception DoesNotExist")
    except Exception as e:
        logging.exception(f"set_progress({task_id}), progress: {prog}, progress_msg: {msg}, got exception: {e}")
```

关键设计点：

1. **进度更新即取消检查**：每次调用 `set_progress` 都会自动调用 `has_canceled(task_id)`，调用方无需显式检查
2. **负进度表示错误**：`prog < 0` 会在消息前添加 `[ERROR]` 前缀，前端可以据此展示错误状态
3. **时间戳自动添加**：所有进度消息自动加上 `HH:MM:SS` 前缀，方便用户了解任务的时间进展
4. **页码范围标注**：支持 `from_page` 和 `to_page` 参数，用于分块处理场景（如「Page(1~10): Extracting entities」）
5. **异常分层处理**：`TaskCanceledException` 立即重新抛出以中断任务，其他异常记录日志后吞掉，避免进度更新失败导致任务挂起

### 7.2 has_canceled：基于 Redis 的取消标记

`api/db/services/task_service.py:649` 实现了取消检测：

```python
def has_canceled(task_id):
    try:
        if REDIS_CONN.get(f"{task_id}-cancel"):
            logging.info(f"Task: {task_id} has been canceled")
            return True
    except Exception as e:
        logging.exception(e)
    return False
```

取消标记由 `cancel_all_task_of` 设置：

```python
def cancel_all_task_of(doc_id):
    abort_doc_chunking_counter(doc_id)
    for t in TaskService.query(doc_id=doc_id):
        try:
            REDIS_CONN.set(f"{t.id}-cancel", "x")  # 值为 "x"，只用于存在性检查
        except Exception as e:
            logging.exception(e)
```

这种实现的特点：

- **Redis 而非数据库**：避免每次检查都触发 SQL 查询，Redis GET 延迟通常在 1ms 以下
- **异常静默降级**：Redis 故障时 `has_canceled` 返回 `False`，任务继续执行而非卡死。这是「可用性优先于一致性」的选择——最坏情况是用户取消操作延迟生效
- **文档级批量取消**：`cancel_all_task_of` 取消某个文档关联的所有任务，用于用户删除文档或重置处理状态的场景

### 7.3 GraphRAG 中的密集取消检查点

GraphRAG 流程通过 `_has_cancel_and_exit` 辅助函数在关键节点插入取消检查：

```python
def _has_cancel_and_exit(task_id: str, message: str, callback=None) -> None:
    if not task_id or not has_canceled(task_id):
        return
    if callback:
        callback(msg=message)
    raise TaskCanceledException(f"Task {task_id} was cancelled")
```

该函数在 `graphrag/general/index.py` 中被调用了 **15 次以上**，覆盖：

| 调用位置（行号） | 阶段 | 原因 |
|----------------|------|------|
| 163 | 重试循环入口 | 避免重试已取消的任务 |
| 195 | 分布式锁等待 | 获取锁可能等待数十秒，需及时响应取消 |
| 362, 368, 375 | 文档批处理 | 每个文档处理前检查，单个文档可能耗时数分钟 |
| 390 | 子图生成 | LLM 密集调用阶段，每批前检查 |
| 439, 455 | 文档批次间隙 | 批次边界是取消的自然断点 |
| 472, 477, 482 | 图合并 | 合并涉及大量内存操作，检查避免无效计算 |
| 545, 574, 606 | 实体消解/社区检测 | 后期阶段耗时长，检查让取消能在阶段边界生效 |

此外，实体提取的 worker 协程也直接检查：

```python

    nonlocal error_count
    async with limiter:
        if task_id and has_canceled(task_id):
            raise TaskCanceledException(f"Task {task_id} was cancelled during entity extraction")
        # ... 实际提取逻辑 ...
```

这保证了即使在高并发的实体提取阶段（数千个 chunk 并发处理），取消检测也能在秒级响应。

### 7.5 取消异常的传播与捕获

`TaskCanceledException` 会穿透整个调用栈直到顶层 worker：

```python
# task_executor.py:1641（embedding 阶段）
try:
    embeddings = []
    for doc_id in doc_ids:
        emb = get_embedding(tenant_id, doc_id)
        embeddings.extend(emb)
        set_progress(task_id, prog=..., msg=...)  # 可能抛出 TaskCanceledException
except TaskCanceledException:
    set_progress(task_id, prog=-1, msg="Task has been canceled.")  # 更新最终状态
    raise  # 重新抛出，让外层 worker 记录取消日志
```

外层 worker 捕获后会：

1. **记录取消日志**：`logging.info(f"Task {task_id} canceled")`
2. **不回滚已完成的工作**：已写入的 chunk、缓存、检查点都保留，支持后续恢复
3. **不更新文档状态为失败**：取消与失败语义不同，前端根据 `progress = -1` 和 `[Canceled]` 标记展示取消状态

### 7.6 进度持久化与前端轮询

`TaskService.update_progress` 将进度写入数据库 `task` 表的 `progress` 和 `progress_msg` 字段。前端通过 REST API 轮询：

```
GET /api/task/{task_id}/status
Response: {
  "progress": 0.5,         // 0~1 的浮点数
  "progress_msg": "14:23:15 Page(1~10): Extracting entities..."

```

轮询间隔为 2-5 秒，避免使用 WebSocket 的原因：

1. **无状态架构**：HTTP 轮询无需维护长连接，服务重启或负载均衡切换不影响进度查询
2. **简化运维**：不需要配置 WebSocket 代理、会话保持、心跳检测
3. **容错性更好**：客户端断线后重连直接拉取最新进度，无需重建订阅
4. **开销可控**：GraphRAG 任务通常运行数分钟到数小时，每 2 秒一次的 SELECT 查询对数据库压力可以忽略

## 8. 总结与设计原则

RAGFlow GraphRAG 的容错与性能设计遵循以下核心原则：

### 8.1 分层超时与快速失败

- **内层短超时**：单次 LLM 调用、单批写入设置严格超时，避免个别慢请求拖累整体
- **外层长超时**：任务级超时作为最后防线，给重试和恢复留出时间
- **快速失败优于静默等待**：超时立即抛异常，让调用方决策（重试/降级/放弃），而非无限等待或返回不完整结果

### 8.2 限流而非拒绝

- **信号量而非速率限制**：`asyncio.Semaphore` 的阻塞式等待保证请求最终会被处理，避免客户端实现复杂的重试逻辑
- **分资源限流**：LLM、嵌入、存储各自独立限流，防止单一资源成为全局瓶颈
- **限流器生命周期管理**：`LoopLocalSemaphore` 解决了 worker 池环境下信号量跨事件循环的问题

### 8.3 缓存优先与过期自治

- **内容寻址缓存**：哈希键保证相同输入必命中，避免参数细微差异导致的重复计算
- **合理的 TTL**：24 小时覆盖重跑场景，7 天覆盖阶段恢复，但不会永久占用内存
- **批量探测优化**：`MGET` 将 N 次查询压缩为 1 次，在大规模场景下缩短等待时间两个数量级

### 8.4 两层恢复与降级容忍

- **阶段标记 + 细粒度检查点**：粗粒度快速跳过整阶段，细粒度精确续传单元
- **恢复失败不阻塞执行**：Redis 故障时检查点加载返回空集，任务从头执行而非挂起
- **部分损坏的检查点仍可用**：单条解析失败不影响其他条目的加载

### 8.5 批量处理与原子性平衡

- **批量大小经验值**：64 在吞吐、请求体积、重试成本间取得平衡
- **批量写入的事务保护**：Redis pipeline 保证索引与数据的一致性，避免孤儿数据
- **并发批次数限制**：4 个并发批次避免写入队列积压，同时充分利用多核

### 8.6 进度可见与取消响应

- **嵌套进度映射**：内层进度线性映射到外层，保证单调递增的用户体验
- **抽样取消检测**：每 10 次循环检查一次，在响应性与性能间折中
- **取消不等于删除**：保留检查点和缓存，支持任务暂停后恢复

### 8.7 防御性设计与静默降级

- **环境变量的边界检查**：`max(1, int(env))` 防止零值和负值导致的除零或死锁
- **可选依赖的版本检查**：`hasattr(redis_client, "pipeline")` 适配不同 Redis 封装
- **日志而非崩溃**：非关键路径的异常记录日志后继续，避免局部故障扩散为全局失败

---

**最终效果**：在典型的 1000 文档、10 万 chunk 规模下，GraphRAG 流程能在 LLM 服务正常的前提下完成端到端处理，中途任意阶段失败后重启任务，已完成的工作通过检查点和缓存自动复用，避免从零开始。单次 LLM 服务故障通过重试自动恢复，持续故障通过超时机制快速失败并暴露给运维人员。

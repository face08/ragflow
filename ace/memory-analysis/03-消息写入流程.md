# RAGFlow Memory 模块 — 消息写入流程

## 1. 写入流程总览

消息写入是同步操作，6 个步骤在单个 HTTP 请求中完成：

```
  POST /v1/memory/{memory_id}/messages
             │
             ▼
  ┌──────────────────────────────────┐
  │ 1. 权限检查与配置获取              │
  │    requireMemoryAccess            │
  └────────────┬─────────────────────┘
               ▼
  ┌──────────────────────────────────┐
  │ 2. 生成唯一消息 ID                │
  │    Redis INCR memory_<id>        │
  └────────────┬─────────────────────┘
               ▼
  ┌──────────────────────────────────┐
  │ 3. 构建原始消息文档                │
  │    buildRawMessage                │
  └────────────┬─────────────────────┘
               ▼
  ┌──────────────────────────────────┐
  │ 4. 写入异步任务记录                │
  │    insertMemoryTask (原子操作)     │
  └────────────┬─────────────────────┘
               ▼
  ┌──────────────────────────────────┐
  │ 5. 向量化并持久化到索引            │
  │    embedAndSave                   │
  └────────────┬─────────────────────┘
               ▼
  ┌──────────────────────────────────┐
  │ 6. 发布 NATS 唤醒消息             │
  │    publishMemoryTaskWakeup        │
  └────────────┬─────────────────────┘
               ▼
         返回 message_id
```

## 2. 权限检查与配置获取

### 2.1 访问权限验证

复用统一的权限检查逻辑（详见 02-创建与配置流程 第 9 节）：

```go
// internal/service/memory.go: QueueSaveToMemoryTask
memory, err := s.requireMemoryAccess(ctx, memoryID, userID)
if err != nil {
    return "", err
}
```

### 2.2 获取模型配置

从 Memory 记录中读取嵌入模型和 LLM 配置：

```go
embdID := memory.EmbdID
llmID := memory.LLMID
systemPrompt := memory.SystemPrompt
temperature := memory.Temperature
```

这些配置在 Memory 创建时固化，确保同一 Memory 下所有消息使用一致的模型。

## 3. 生成唯一消息 ID

### 3.1 Redis 自增计数器

使用 Redis 的 `INCR` 命令生成全局递增的消息 ID：

```go
// internal/service/memory_message_service.go: generateRawMessageID
key := fmt.Sprintf("memory_%s", memoryID)
messageID, err := redis.Incr(ctx, key).Result()
if err != nil {
    return 0, err
}
return messageID, nil
```

优势：
- **原子性**：Redis INCR 是原子操作，并发安全
- **顺序性**：消息 ID 严格递增，反映写入时序
- **轻量级**：无需查询数据库，性能高

### 3.2 ID 格式约定

最终的文档 ID 格式为：`<memory_id>_<message_id>`

例如：`a1b2c3d4_00000042` 表示 Memory `a1b2c3d4` 的第 42 条消息。

## 4. 构建原始消息文档

### 4.1 内容格式化

将用户输入和 Agent 响应合并为单一文本：

```go
// internal/service/memory_message_service.go: buildRawMessage
content := fmt.Sprintf("User Input: %s\nAgent Response: %s",
    req.UserInput, req.AgentResponse)
```

这种格式的设计意图：
- LLM 提取时能清晰区分对话双方
- 检索时用户输入和响应作为整体匹配，保留上下文完整性

### 4.2 文档字段结构

```go
doc := map[string]interface{}{
    "id":            fmt.Sprintf("%s_%d", memoryID, messageID),
    "memory_id":     memoryID,
    "tenant_id":     tenantID,
    "message_id":    messageID,
    "memory_type":   MemoryTypeRaw,   // 原始消息类型
    "content":       content,
    "user_input":    req.UserInput,
    "agent_response": req.AgentResponse,
    "session_id":    req.SessionID,
    "user_id":       req.UserID,
    "create_time":   time.Now().UnixMilli(),
    "create_date":   time.Now().Format(time.RFC3339),
    "source_id":     "",              // 原始消息无来源
    "forget_at":     0,               // 0 表示未遗忘
}
```

字段说明：

| 字段 | 类型 | 用途 |
|------|------|------|
| id | string | 文档主键，格式 `<memory_id>_<message_id>` |
| memory_id | string | 所属 Memory，过滤条件 |
| memory_type | int | 位标志，区分原始/提取记忆 |
| content | string | 检索的主文本字段 |
| session_id | string | 会话隔离，支持按会话检索 |
| user_id | string | 终端用户标识，支持多用户记忆隔离 |
| source_id | string | 提取记忆指向的原始消息 ID，原始消息为空 |
| forget_at | int64 | 软删除时间戳，0 表示有效 |

### 4.3 向量字段

嵌入向量字段名带维度后缀，兼容多模型：

```go
// 例如 1024 维模型
vectorField := fmt.Sprintf("q_%d_vec", vectorSize)
doc[vectorField] = embedding
```

这样同一索引下可以存放不同维度的向量（虽然实际上单个 Memory 固定一种模型）。

## 5. 写入异步任务记录

### 5.1 原子插入

任务记录和原始消息必须同时成功，使用数据库事务保证：

```go
// internal/service/memory_message_service.go: insertMemoryTask
task := &entity.MemoryTask{
    ID:          common.GenerateUUID(),
    MemoryID:    memoryID,
    TenantID:    tenantID,
    RawID:       rawDocID,
    State:       "pending",
    Progress:    0,
    Attempts:    0,
    NextRunAt:   time.Now(),
    CreateTime:  time.Now().UnixMilli(),
}

err := s.memoryTaskDAO.Insert(ctx, task)
```

### 5.2 任务状态机初始值

新建任务的初始状态：

| 字段 | 初始值 | 说明 |
|------|--------|------|
| state | "pending" | 等待被工作者领取 |
| progress | 0 | 进度 0% |
| attempts | 0 | 尝试次数 |
| next_run_at | now | 立即可执行 |
| lease_owner | "" | 无持有者 |
| lease_expire_at | 0 | 无租约 |

## 6. 向量化并持久化到索引

### 6.1 嵌入模型调用

使用 Memory 配置的嵌入模型生成向量：

```go
// internal/service/memory_message_service.go: embedAndSave
embdModel, err := s.llmDAO.GetByID(ctx, memory.EmbdID)
if err != nil {
    return err
}

embedding, err := s.embeddingClient.Embed(ctx, &EmbedRequest{
    Model: embdModel.Name,
    Input: content,
})
if err != nil {
    return fmt.Errorf("embedding failed: %w", err)
}
```

### 6.2 写入文档引擎

根据 Memory 的租户 ID 确定索引名：

```go
// internal/service/memory_message_service.go: embedAndSave
indexName := fmt.Sprintf("memory_%s", memory.TenantID)

// Infinity 引擎追加 memory_id 后缀
if docStore.EngineType() == "infinity" {
    indexName = fmt.Sprintf("%s_%s", indexName, memoryID)
}

err = docStore.Insert(ctx, indexName, []map[string]interface{}{doc})
if err != nil {
    return fmt.Errorf("doc store insert failed: %w", err)
}
```

索引命名规则（详见 01-架构总览 6.1 节）：

| 引擎类型 | 索引名规则 | 示例 |
|----------|-----------|------|
| Elasticsearch / OceanBase / GaussDB | `memory_<tenant_id>` | `memory_user123` |
| Infinity | `memory_<tenant_id>_<memory_id>` | `memory_user123_abc456` |

### 6.3 更新记忆大小缓存

写入成功后，累加消息内容字节数到 Redis 缓存：

```go
// internal/service/memory_message_service.go: embedAndSave
sizeKey := fmt.Sprintf("memory_%s", memoryID)
contentSize := len([]byte(content))

redis.IncrBy(ctx, sizeKey, int64(contentSize))
```

这个缓存用于快速检查是否超过配额（`memory_size` 字段），避免每次都扫描索引计算总大小。

## 7. 发布 NATS 唤醒消息

### 7.1 消息格式

通知异步工作者有新任务待处理：

```go
// internal/service/memory_message_service.go: publishMemoryTaskWakeup
msg := &MemoryTaskWakeup{
    TaskID:   task.ID,
    MemoryID: memoryID,
    TenantID: tenantID,
}

err = s.natsClient.Publish(ctx, "memory.task.wakeup", msg)
```

### 7.2 主题订阅者

异步提取服务订阅 `memory.task.wakeup` 主题，收到消息后立即尝试领取任务（详见 04-异步提取流程）。

### 7.3 容错设计

即使 NATS 发布失败，任务记录已写入数据库，调度器的定期扫描（ReconcileMemoryTasks）会兜底执行，最多延迟 30 秒。

## 8. 同步与异步的边界

写入流程的关键设计是划分同步和异步职责：

| 阶段 | 执行方式 | 原因 |
|------|----------|------|
| 消息 ID 生成 | 同步 | 需立即返回给调用方 |
| 原始消息向量化 | 同步 | 保证写入即可检索 |
| 原始消息入索引 | 同步 | 数据不丢失的最低保证 |
| LLM 记忆提取 | 异步 | LLM 调用耗时长（数秒到数十秒） |
| 提取记忆入索引 | 异步 | 依赖提取结果 |

这种划分让 HTTP 请求在数百毫秒内返回，同时保证原始消息不会因为 LLM 服务不可用而丢失。

## 9. Python 侧实现对照

Python 侧的写入逻辑与 Go 侧功能一致：

```python
# api/db/joint_services/memory_message_service.py
async def queue_save_to_memory_task(
    memory_id: str, user_input: str, agent_response: str,
    session_id: str, user_id: str, tenant_id: str
) -> str:
    # 1. 获取配置
    memory = MemoryService.get_by_id(memory_id)
    
    # 2. 生成消息 ID
    message_id = REDIS_CONN.incr(f"memory_{memory_id}")
    
    # 3. 构建文档
    doc = build_raw_message(memory_id, message_id, user_input,
                             agent_response, session_id, user_id)
    
    # 4. 插入任务
    task_id = MemoryTaskService.insert_task(memory_id, doc["id"], tenant_id)
    
    # 5. 向量化并写入
    await embed_and_save(doc, memory)
    
    # 6. 发布唤醒
    await publish_memory_task_wakeup(task_id, memory_id, tenant_id)
    
    return doc["id"]
```

两个运行时共享同一套数据表和索引结构，可以互相接管任务。

# RAGFlow 文本（TXT）文档解析完整流程

## 场景设定

假设我们有一个技术文档 `user_manual.txt`（UTF-8 编码），内容如下：

```
系统架构设计

本系统采用微服务架构，主要包含以下模块：

API Gateway模块
负责统一入口管理和请求路由。主要功能包括：认证、限流、负载均衡。

数据处理模块
采用异步消息队列进行数据处理。支持批量导入和实时同步两种模式。

存储层设计
使用MySQL作为主数据库，Redis作为缓存层。数据备份策略：每日全量+实时增量。

常见问题

Q: 如何配置数据库连接？
A: 在config.yaml中配置database.url参数。

Q: 系统支持哪些认证方式？
A: 支持OAuth2.0、JWT和API Key三种认证方式。
```

该文档共约 180 个 token。

---

## 流程概览

TXT 文档解析流程比 PDF 简单得多，因为纯文本文档没有复杂的布局、表格、图片等结构，主要是**文本编码检测 → 分隔符切分 → 段落合并 → 分块 → 最终 Chunk 生成**。

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         TXT 解析 Pipeline                                 │
├──────────────────────────────────────────────────────────────────────────┤
│  原始文件 (bytes)                                                         │
│       ↓                                                                  │
│  阶段1: 编码检测与解码 (decode_text / find_codec)                        │
│       ↓                                                                  │
│  阶段2: 换行符规范化 (normalize_text_newlines)                           │
│       ↓                                                                  │
│  阶段3: 分隔符解析与切分 (parse_delimiter_field + re.split)              │
│       ↓                                                                  │
│  阶段4: 段落合并 (merge_paragraphs with OVER_CAP strategy)               │
│       ↓                                                                  │
│  阶段5: 生成初步 sections [[text, ""]]                                    │
│       ↓                                                                  │
│  阶段6: RTL 表示形式规范化 (normalize_arabic_presentation_forms)          │
│       ↓                                                                  │
│  阶段7: 分词与向量化 (tokenize_chunks)                                    │
│       ↓                                                                  │
│  最终 Chunk 对象 (content_ltks, content_sm_ltks, q_768_vec, etc.)        │
└──────────────────────────────────────────────────────────────────────────┘
```

## 阶段 1: 编码检测与解码

**代码入口**: `rag/nlp/__init__.py::decode_text()` / `find_codec()`

**数据库存储**: ❌ **不存储** - 这是纯内存操作，编码检测结果不持久化

TXT 文件的字节流需要先检测编码格式，然后解码为 Unicode 字符串。

### 输入

- **二进制数据**:
  ```python
  binary = b'\xe7\xb3\xbb\xe7\xbb\x9f\xe6\x9e\xb6\xe6\x9e\x84\xe8\xae\xbe\xe8\xae\xa1\n\n\xe6\x9c\xac...'
  ```
  （原始 UTF-8 字节流）

### 处理逻辑

1. **BOM 检测**: 检查文件开头是否有 BOM（Byte Order Mark）
   - `\xef\xbb\xbf` → UTF-8-sig
   - `\xff\xfe` → UTF-16-LE
   - `\xfe\xff` → UTF-16-BE
   - `\xff\xfe\x00\x00` → UTF-32-LE
   - `\x00\x00\xfe\xff` → UTF-32-BE

2. **UTF-8 优先尝试**: 如果没有 BOM，先尝试 UTF-8 解码

   ```python
   try:
       return blob.decode("utf-8"), "utf-8"
   except UnicodeDecodeError:
       pass
   ```

3. **chardet 自动检测**: 使用 chardet 库检测编码（采样前 1024 字节）

   ```python
   detected = chardet.detect(blob[:1024])
   encoding = detected.get("encoding")  # 例如: "utf-8", "gb18030", "iso-8859-1"
   confidence = detected.get("confidence")  # 0.0 ~ 1.0
   ```

4. **GBK/GB2312 规范化**: 如果检测到 GBK/GB2312，统一使用 GB18030（向后兼容）

   ```python
   if encoding and encoding.lower().replace("-", "") in {"gb2312", "gbk"}:
       encoding = "gb18030"
   ```

5. **置信度阈值**: 如果置信度低于 0.8，抛出异常
   ```python
   if not encoding or confidence < 0.8:
       raise UnicodeError(f"Unable to reliably detect text encoding (confidence={confidence:.2f})")
   ```

### 输出

- **解码后的文本**:

```python
  text = """系统架构设计

本系统采用微服务架构，主要包含以下模块：

API Gateway模块
负责统一入口管理和请求路由。主要功能包括：认证、限流、负载均衡。

数据处理模块
采用异步消息队列进行数据处理。支持批量导入和实时同步两种模式。

存储层设计
使用MySQL作为主数据库，Redis作为缓存层。数据备份策略：每日全量+实时增量。

常见问题

Q: 如何配置数据库连接？
A: 在config.yaml中配置database.url参数。

Q: 系统支持哪些认证方式？
A: 支持OAuth2.0、JWT和API Key三种认证方式。"""

  encoding = "utf-8"
```

## 阶段 2: 换行符规范化

**代码入口**: `rag/nlp/delim.py::normalize_text_newlines()`

**数据库存储**: ❌ **不存储** - 这是纯内存操作，规范化结果不持久化

将不同操作系统的换行符统一为 Unix 风格的 `\n`。

### 输入

来自阶段 1 的 Unicode 字符串（可能包含 `\r\n` 或 `\r`）

### 处理逻辑

```python
def normalize_text_newlines(text: str) -> str:
    if not text:
        return text
    return text.replace("\r\n", "\n").replace("\r", "\n")
```

- Windows 风格 `\r\n` → `\n`
- Mac 旧版风格 `\r` → `\n`

### 输出

标准化后的文本（所有换行符都是 `\n`）

## 阶段 3: 分隔符解析与切分

**代码入口**:

- `rag/nlp/delim.py::parse_delimiter_field()`
- `rag/nlp/delim.py::compile_delimiter_pattern()`
- `deepdoc/parser/txt_parser.py::RAGFlowTxtParser.parser_txt()`

**数据库存储**: ❌ **不存储** - 这是纯内存操作，段落切分结果不持久化

根据用户指定的分隔符（默认 `"\n!?;。；！？"`）切分文本。

### 输入

- **文本**: 阶段 2 的规范化文本
- **分隔符配置**: `delimiter = "\n!?;。；！？"`（默认）
- **chunk_token_num**: `128`（默认块大小）

### 处理逻辑

#### 3.1 解析分隔符字段

分隔符字段支持两种语法：

- **裸字符**: 每个字符是独立的分隔符（如 `\n`、`!`、`?`）
- **反引号包裹**: 多字符组合为一个分隔符（如 `` `##` ``）

```python
def parse_delimiter_field(s: str) -> list[str]:
    # 输入: "\n!?;。；！？"
    # 输出: ['\n', '!', '?', ';', '。', '；', '！', '？']

    normalized = normalize_text_newlines(s)  # CRLF → LF
    delimiters = []
    seen = set()

    # 提取反引号包裹的 token
    for match in _BACKTICK_RE.finditer(normalized):
        token = match.group(1)
        if token and token not in seen:
            seen.add(token)
            delimiters.append(token)

    # 提取裸字符
    for ch in normalized:
        if ch not in seen and ch != '`':
            seen.add(ch)
            delimiters.append(ch)

    # 按长度降序排序（确保 `##` 在 `#` 之前匹配）
    return sorted(delimiters, key=len, reverse=True)
```

#### 3.2 编译正则模式

```python
def compile_delimiter_pattern(delimiters: list[str]) -> str:
    # 输入: ['\n', '!', '?', ';', '。', '；', '！', '？']
    # 输出: r'\n|\!|\?|\;|。|；|！|？'
    return "|".join(re.escape(d) for d in delimiters if d)
```

#### 3.3 切分文本

```python
dels = compile_delimiter_pattern(parsed_dels)
# dels = r'\n|\!|\?|\;|。|；|！|？'

secs = re.split(r"(%s)" % dels, txt) if dels else [txt]
# 使用捕获组 (%s)，分隔符也会出现在结果中
```

## 阶段 4: 段落合并（merge_paragraphs）

**代码入口**: `rag/nlp/__init__.py::merge_paragraphs()`

将分隔符切分后的小段落合并为符合 token 预算的更大块。

### 输入

- **paragraphs**: 阶段 3 的段落列表
- **chunk_token_num**: `128`（目标块大小）
- **strategy**: `MergeStrategy.OVER_CAP` 或 `MergeStrategy.UNDER_CAP`

### 合并策略说明

RAGFlow 提供两种段落合并策略，通过 `MergeStrategy` 枚举控制：

| 策略 | 描述 | 是否允许溢出 | 适用场景 |
|------|------|------------|---------|
| **OVER_CAP** | 贪婪模式，允许一次边界溢出 | ✓ | **默认策略**，适合需要保持段落完整性的场景 |
| **UNDER_CAP** | 严格模式，不允许任何溢出 | ✗ | 需要严格控制块大小上限的场景 |

### 处理逻辑

#### 4.1 OVER_CAP 策略（默认，贪婪模式）

**规则**:

- 贪婪地累加相邻段落，只要当前累计 token 数 ≤ `chunk_token_num`
- 当累计 token 超过阈值（`threshold = chunk_token_num * (100 - overlapped_percent) / 100`）时，仍会尝试添加下一个段落
- **关键特性：允许一次边界溢出** —— 当累计 token 已超过阈值时，才关闭当前块并开启新块
- 如果单个段落本身就超过 `chunk_token_num`，它会独立成为一个块

**优点**: 保持段落完整性，避免因严格限制而产生过多碎片块

**缺点**: 块的实际大小可能超过 `chunk_token_num`（但模型层会截断）

```python
def _merge_paragraph_groups(paragraphs, token_size, strategy, size, overlapped_percent=0):
    threshold = token_size * (100 - overlapped_percent) / 100.0  # 重叠场景下的缩减阈值
    groups = []

    cur, cur_t = [], 0
    for i in range(len(paragraphs)):
        pt = size(paragraphs[i])  # 当前段落的 token 数

        # 情况1: 单个段落超过上限，独立成块
        if pt > token_size:
            if cur:
                groups.append(cur)
            groups.append([i])
            cur, cur_t = [], 0
            continue

        # 情况2: 第一个段落，直接加入
        if not cur:
            cur, cur_t = [i], pt
            continue

        # 情况3: 当前累计已超过阈值，关闭当前块，开启新块
        if cur_t > threshold:
            groups.append(cur)
            cur, cur_t = [i], pt
        # 情况4: 继续累加
        else:
            cur.append(i)
            cur_t += pt

    if cur:
        groups.append(cur)

    return groups
```

#### 4.2 UNDER_CAP 策略（严格模式）

**规则**:

- 只有当 `累计 token + 下一段落 token ≤ chunk_token_num` 时才合并
- **严格不允许溢出**：任何会导致超出上限的段落都会开启新块
- 如果单个段落本身就超过 `chunk_token_num`，它独立成块后立即关闭（不与后续段落合并）
- 不使用 `overlapped_percent` 缩减阈值，直接以 `cap = token_size` 为界

```python
if strategy == MergeStrategy.UNDER_CAP:
    cur = []
    cur_tokens = 0
    for i in range(n):
        p = paragraphs[i]

        # 情况1: 当前块为空，放入第一个段落
        if not cur:
            cur = [i]
            cur_tokens = size(p)
            # 单段落超限：立即独立成块并清空
            if cur_tokens > cap:
                groups.append(cur)
                cur = []
                cur_tokens = 0
            continue

        # 情况2: 加入后仍不超限，继续累加
        if cur_tokens + size(p) <= cap:
            cur.append(i)
            cur_tokens += size(p)
        # 情况3: 加入后会超限，关闭当前块，用该段落开启新块
        else:
            groups.append(cur)
            cur = [i]
            cur_tokens = size(p)
            # 新块的首个段落即超限，立即独立成块
            if cur_tokens > cap:
                groups.append(cur)
                cur = []
                cur_tokens = 0

    if cur:
        groups.append(cur)
    return groups
```

```python

    [0, 1, 2, 3, 4, 5, 6, 7],  # 块1: 140 tokens（超出 128）
    [8, 9, 10, 11, 12]         # 块2: 72 tokens
]

# UNDER_CAP（严格）

    [0, 1, 2, 3, 4, 5, 6],           # 块1: 108 tokens（未超限）
```

**优点**: 严格保证每个块不超过 `chunk_token_num`，无需依赖模型层截断

**缺点**: 边界处会更早切断，可能产生更多的块

#### 4.3 策略选择建议

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| 通用 RAG 检索 | `OVER_CAP` | 保持段落语义完整，少量溢出可由模型层截断处理 |
| 严格 token 预算控制 | `UNDER_CAP` | 避免超出下游模型的上下文窗口 |
| 带重叠的分块（JSON 统一策略） | `OVER_CAP` | 仅 `OVER_CAP` 支持 `overlapped_percent` 缩减阈值，为重叠前缀预留空间 |

```python
def _normalize_section_text_for_rtl_presentation_forms(sections):
```

## 阶段 7: 分词与向量化

**代码入口**: `rag/nlp/__init__.py::tokenize_chunks()`

对每个 section 进行分词、生成向量、计算元数据。

### 输入

- **sections**: 阶段 6 的 sections
- **doc**: 文档元数据（`doc_id`, `kb_id`, `parser_config`, etc.）
- **is_english**: 布尔值（判断文档主要语言）

### 处理逻辑

```python
def tokenize_chunks(sections, doc, is_english, language=None):
    res = []
    tokenize_fn = naive_merge_en if is_english else naive_merge_zh

    for sec_idx, (section_text, _) in enumerate(sections):
        # 1. 使用分词器生成 token 列表
        tks = rag_tokenizer.tokenize(section_text)
        # tks: ['系统', '架构', '设计', '\n', '本', '系统', '采用', '微', '服务', '架构', ...]

        # 2. 生成 content_ltks（分词后的文本，用于 BM25 检索）
        content_ltks = rag_tokenizer.fine_grained_tokenize(tks)
        # content_ltks: '系 统 架 构 设 计 本 系 统 采 用 微 服 务 架 构 ...'

        # 3. 生成 content_sm_ltks（更细粒度的分词，用于召回）
        content_sm_ltks = rag_tokenizer.tokenize(section_text, fine_grained=True)

        # 4. 生成向量（使用 embedding 模型）
        q_768_vec = embedding_model.encode(section_text)
        # q_768_vec: array([0.123, -0.456, 0.789, ...], shape=(768,))

        # 5. 构建 Chunk 对象
        chunk = {
            "content_with_weight": section_text,
            "content_ltks": content_ltks,
            "content_sm_ltks": content_sm_ltks,
            "q_768_vec": q_768_vec.tolist(),
            "doc_id": doc["doc_id"],
            "kb_id": doc["kb_id"],
            "important_kwd": [],  # TXT 文档没有特殊关键词提取
            "create_time": datetime.now(),
            "create_timestamp_flt": time.time(),
            "doc_type_kwd": "text",  # 标记为纯文本类型

            # TXT 文档没有页码和位置信息
            "page_num_int": [],
            "position_int": [],
            "top_int": [],
            "positions": ""
        }

        res.append(chunk)

    return res
```

### 检索流程

**用户查询**: "如何配置数据库连接？"

1. **向量检索**:
   - 将查询向量化: `query_vec = embedding("如何配置数据库连接")`
   - 执行 kNN 搜索: `q_768_vec` 字段的余弦相似度
2. **BM25 检索**:
   - 对查询分词: `["如何", "配置", "数据库", "连接"]`
   - 在 `content_ltks` 字段进行全文检索
3. **混合排序**:
   - 向量得分 × 0.7 + BM25 得分 × 0.3
   - 返回 Top-K 结果

4. **高亮回溯**:
   - **TXT 文档没有 `positions` 信息**，无法进行原文坐标高亮
   - 只能返回整个 Chunk 的文本内容
   - 前端可以使用简单的文本匹配高亮（基于关键词）

## TXT 与 PDF 解析的核心差异

| 维度           | PDF 解析                                     | TXT 解析                             |
| -------------- | -------------------------------------------- | ------------------------------------ |
| **复杂度**     | 高（7阶段：OCR、布局、表格、合并等）         | 低（4阶段：编码、切分、合并、分词）  |
| **布局分析**   | 需要识别标题、段落、表格、图片               | **无需布局分析，纯文本流**           |
| **OCR**        | 需要（扫描版PDF）                            | **不需要**                           |
| **表格识别**   | 需要（识别行列结构）                         | **不支持表格**                       |
| **图片提取**   | 需要提取嵌入图片                             | **不支持图片**                       |
| **坐标信息**   | 有（bbox, top, bottom, page）                | **无坐标信息**                       |
| **分块策略**   | 基于布局 + token 数                          | **仅基于分隔符 + token 数**          |
| **最终 Chunk** | `doc_type_kwd` 可能为 `text`/`table`/`image` | **固定为 `text`**                    |
| **高亮回溯**   | 支持原文坐标高亮                             | **不支持坐标高亮，只能文本匹配**     |
| **适用场景**   | 结构化文档、扫描件、多媒体内容               | **纯文本日志、代码、配置文件、小说** |

## 关键设计原则

1. **分隔符是 Chunk 边界的硬约束**:
   - 分隔符文本（如 `\n`, `。`, `!`, `?`）**永远不会进入 Chunk 内容**
   - 保证语义完整性，避免句子被切断

2. **token_size 是软目标**:
   - `OVER_CAP` 策略允许超出一次（贪婪合并）
   - `UNDER_CAP` 策略严格遵守上限
   - 超长段落不会被强制切分（交给模型层截断）

3. **纯文本流特性**:
   - 没有坐标、页码、布局信息
   - 适合日志、代码、配置文件等纯文本场景
   - 无法支持原文定位高亮（只能文本匹配）

4. **编码鲁棒性**:
   - 支持 BOM 检测、UTF-8 优先、chardet 自动检测
   - GBK/GB2312 统一规范化为 GB18030
   - 置信度阈值保证解码质量

## 总结

TXT 文档解析是 RAGFlow 中最**简单**的解析流程，核心步骤只有：

1. **编码检测与解码**（UTF-8/GBK/GB18030 自动识别）
2. **换行符规范化**（CRLF → LF）
3. **分隔符切分**（用户指定，默认 `\n!?;。；！？`）
4. **段落合并**（OVER_CAP 贪婪策略）
5. **分词向量化**（生成 BM25 token 和 embedding 向量）

相比 PDF 的 7 阶段复杂流程，TXT 解析**无需 OCR、布局分析、表格识别**，但也牺牲了**原文定位**和**多媒体支持**能力。

适用场景：

- ✅ 日志文件、代码文件、配置文件
- ✅ 纯文本小说、文章、笔记
- ✅ Markdown 文本（作为纯文本处理）
- ❌ 扫描件、PDF 文档、Word 文档
- ❌ 需要表格/图片提取的文档
- ❌ 需要原文定位高亮的场景
